# 场景与 3D 资产

> 模型怎么从 Blockbench 出来变成能跑的 glTF / glb、贴图怎么调、动画怎么裁、
> 以及后期渲染和抗锯齿那几个把人坑过的坑。
>
> 返回 [项目主 README](../README.md)
## 模型与动画优化

原文件 `peekdeek.gltf` **10.8 MB**（722 节点、567 个方块网格、151 个动画），
优化后的 `peekdeek_opt.glb` **1.30 MB**，**小了 7.9 倍**。

原始文件和它的 import 都**原样保留**，没有覆盖。

### 数据是怎么省下来的

分析结果（用 `tools/analyze_gltf.mjs` 量的）：6.83 MB 的二进制数据里有 **6.07 MB 是动画**，
而且两个动画严重注水：

| 动画 | 关键帧 | 时长 | 问题 |
| --- | --- | --- | --- |
| `MainAnim` | 282,882 | **4,312 秒** | 实际只是 4 条轨道在轻微呼吸摆动，导出时被拉成了 72 分钟 |
| `hold_mainhand$minecraft:mace` | 32,235 | **1,000 秒** | 同上，桌宠完全用不到 |

另外整个 buffer 是以 **base64 内嵌**在 JSON 里的（912 万字符），光编码开销就很可观。

优化做了四件事：

1. **glTF → GLB**：二进制 buffer 不再 base64，直接省掉三分之一
2. **砍掉用不到的动画**：151 → 33，桌面宠物真正需要的只有这些
3. **`MainAnim` 限时重采样**：4,312 秒 / 28 万帧 → **24 秒 @ 8Hz**，只留 772 帧，
   呼吸摆动的手感保留下来，体积从 5.13 MB 降到几 KB
4. **删掉恒定不变的轨道**：共 550 条，这些轨道不携带任何信息
   （Godot 导入时也会做，但先删掉能少让编辑器啃一堆数据）

**没有动的东西**：节点层级、节点名、网格、材质、UV、贴图。所以所有保留下来的动画
依然驱动着完全相同的节点。

### 保留下来的 33 个动画

- **基础**：`idle` `walk` `walkBack` `run` `jump` `sneak` `sit` `sleep` `climb` `swim` `fly` `death` `attacked`
- **互动**：`use_mainhand` `use_offhand` `swing_hand` `swing_offhand` `BlinkEye` `BlinkTwo`
- **表情动作**：`extra0` `extra2`~`extra7`
- **其他**：`MainAnim`（已重采样）、`ladder_up/down/stillness`

`idle` 和 `MainAnim` 在运行时被合并成一个 `__pet_idle`：`MainAnim` 是 24 秒的呼吸摆动，
压到 `idle` 的 3 秒周期上，两条循环就对齐了，互不冲突的轨道才会被合并
（见 `scripts/desktop_pet.gd` 的 `_build_idle_anim()`）。

眨眼动画被放进**第二个 AnimationPlayer**（运行时创建），且拷入时用 `_strip_to_face()`
裁到只剩 `/Face/` 下的轨道 —— 因为原始 `BlinkEye`/`BlinkTwo` 其实覆盖全身（39 条轨道），
不裁的话走路中眨眼会把全身钉成站立姿势（见下文「走着走着突然变成静止姿势在滑行」）。

### 动画的两个坑

**1. 持续动作必须手动开循环。** 导出的 glb 里动画 `loop_mode` 默认是 `LOOP_NONE`，
播完就停在最后一帧 —— 走路/跑步"走到一半突然定住"就是这么来的。
`_apply_loop_modes()` 启动时把 `LOOPING_ANIMS` 里那些持续动作统一设成
`LOOP_LINEAR`（实测打开 14 个）。顺带也修掉了 `sit` / `sleep`：它俩长度只有
0.001 秒，之前播完会立刻触发 `animation_finished` 被弹回待机。

**2. 一次性动作的等待时间要按动画自身长度算，不能写死。** 实测：

| 动画 | 长度 | 旧写死值 | 结果 |
| --- | --- | --- | --- |
| jump / swing_hand / attacked / use_mainhand | 0.375 ~ 0.75s | 0.6 ~ 1.2s | 够 |
| extra0 ~ extra6 | 1.0 ~ 1.5s | 1.6s | 够 |
| **extra7** | **7.5s** | 1.6s | **播到 1.6 秒就被切走** |

所以改成 `_play_action()`：等待时间 = `动画长度 / anim_speed + 缓冲`。

### 修掉的两处模型/交互毛病

**1. 左腿骨骼下混着右腿的方块**（"有一只脚的部分方块跟着另一只脚走"）

用 `tools` 里的分析脚本把小腿三层骨骼下的方块坐标全列了一遍，发现左脚骨骼
（`LeftFoot13`）下挂着一块 `local_x = +0.119` 的方块 —— 模型中线在 x=0，左腿在负侧，
所以这块其实长在**右腿**那边，却跟着左腿摆动。

而右脚骨骼下已经有一块位置**完全相同**的方块（`RightFoot7`，同为 0.119），
所以它是个重复件。`desktop_pet.gd` 的 `_fix_crossed_leg_parts()` 在 `_ready()` 里
按位置做了一次校正：另一侧已有同位置方块就移除，否则挪过去并保持世界变换 ——
两种情况都不改变静止姿势，只修正"跟随哪条腿"。

顺带一提，排查时有个坑：**Godot 导入 glb 会给重名节点加数字后缀**，
骨骼实际叫 `LeftLeg9` / `LeftFoot13` / `RightFoot11`，用精确名字是找不到的，
只能用前缀匹配 + "该节点直接挂着 MeshInstance3D"来识别骨骼（方块节点也叫
`LeftFoot4` 这类名字，但它们是叶子）。

**2. 鼠标碰到角色时窗口会闪一下**

原来的做法是在"整窗可点"和"整窗穿透"之间切换，靠 `window_set_mouse_passthrough()`
来回设区域。这个 API 的参数是**接受鼠标事件的区域**，每次调用都会让 Windows
重建窗口区域，闪的那一下就是这么来的。

现在改成把可点区域**固定成角色所在的矩形**（外扩 `catch_padding`），只在包围盒
真的变化（>1.5px）时才更新；鼠标进出角色完全不动窗口，空白处照样穿透。

## 后期渲染 / 抗锯齿收敛（白边问题）

原来的配置会在轮廓上出现一圈偏白的描边。查下来是**三个设置叠在一起**造成的，
其中最主要的一个是贴图导入参数：

### 根因

把贴图拆出来量了一下：256×256，**完全不透明 31.4%、完全透明 68.6%、半透明 0%**
——是一张硬边像素画，alpha 只有 0 和 1 两种值。

但是那圈"完全透明、又紧贴着图案"的 texel，RGB **并不是黑色**：

| | 透明环平均亮度 | 其中偏亮的比例 |
| --- | --- | --- |
| 修复前 | **0.638** | **49.8%** |
| 修复后 | **0.000** | **0%** |

也就是说，轮廓外面那一圈 texel 里存着大量接近白色的 RGB。原来的贴图导入设置是：

```
compress/mode=2            # VRAM 压缩 S3TC/BPTC
mipmaps/generate=true      # 生成 mipmap
process/fix_alpha_border=true   # 把边缘颜色扩散进透明区
```

`fix_alpha_border` 会把图案边缘的颜色向透明区扩散，配上 VRAM 压缩和 mipmap 的
多次降采样，那圈透明 texel 就被填成了亮色。而方块模型用的是**线性过滤**，
每个方块的边缘都会采到这一圈 —— 于是整圈轮廓被掺进了白色，看起来就是"抗锯齿白边"。

### 改了什么

**贴图导入**（`peekdeek_opt_0.png.import`）：

| 参数 | 原来 | 现在 | 原因 |
| --- | --- | --- | --- |
| `compress/mode` | 2（VRAM/S3TC） | **0（无损）** | 贴图才 30 KB，压缩省不了空间，反而在色块边界产生伪影 |
| `mipmaps/generate` | true | **false** | 像素画用不上 mipmap，降采样只会把透明区颜色混进边缘 |
| `process/fix_alpha_border` | true | **false** | 就是它把亮色填进透明环的 |

**采样方式**：材质的 `texture_filter` 设成 `TEXTURE_FILTER_NEAREST`。
方块模型的每一个面都是轴对齐的矩形，UV 正好落在 texel 边界上，最近邻采样最准、
也彻底不会串色（这也是 Minecraft 类画风的通行做法）。
代码里在 `desktop_pet.gd` 的 `_harden_materials()` 统一设置，566 个 surface 共用 1 个材质。

> 顺带记一下：**Godot 4 的 PNG 导入面板里没有"采样过滤（Filter）"这一项**。
> 导入面板能控的只有 mipmap、压缩方式、fix alpha border、normal map 这些；
> 采样过滤只存在于**材质**的 `texture_filter` 和项目默认的
> `rendering/textures/default_filters/`（那里也只有各向异性等级和
> use_nearest_mipmap_filter，没有 3D 的 Filter 选项）。
> 所以"把 Filter 改成 Nearest"这件事，在这个项目里是在代码里做的。

**抗锯齿**：

这个模型是"方块 + 像素画贴图"，锯齿其实有两个来源，得分开治：

| 锯齿来源 | 用什么治 | 说明 |
| --- | --- | --- |
| 几何边缘（方块轮廓、斜角） | MSAA | 只跟三角形边界有关，贴图设置帮不上忙 |
| 贴图镂空边缘 | alpha scissor | alpha **混合**的边缘 MSAA 是无效的，改成 scissor 才吃抗锯齿 |

对应设置：

| 设置 | 原来 | 现在 | 原因 |
| --- | --- | --- | --- |
| `anti_aliasing/quality/msaa_3d` | 2（4x） | **3（8x）** | 轮廓锯齿交给 MSAA，它只作用在几何边缘 |
| `anti_aliasing/quality/screen_space_aa` | 1（FXAA） | **0** | 它在透明背景下只磨 RGB 不磨 alpha，会把轮廓掺黑 —— 见下文「透明背景下别用 SMAA / FXAA」 |
| `scaling_3d/scale` | 1.0 | **2.0（2 倍超采样）** | 用来压方块之间的亚像素缝隙，见下 |
| `environment/defaults/default_clear_color` | 默认 | 保持默认 | 实测改它对这个透明窗口没有任何影响 |

**超采样（`scaling_3d/scale = 2.0`）**：内部按 660×940 渲染，再降采样回 330×470。
整数倍超采样对像素画本身是安全的（方块面 UV 落在 texel 边界上，2×2 降采样不跨边界），
它主要用来减轻**方块之间那些亚像素缝隙**造成的白线（成因见下面的 TAA 一节）。

代价是过渡像素变多、而且平均亮度偏高：

| | 轮廓上的过渡像素 | 这些过渡像素的平均亮度 |
| --- | --- | --- |
| `scale = 1.0`（8x MSAA） | 659 | 0.555 |
| `scale = 2.0`（8x MSAA + 2x SSAA） | 807 | 0.624 |

也就是轮廓外会多出一层很淡的过渡带。两害相权，白线比这层过渡带扎眼得多，
所以留着开着；不想要的话把 `scaling_3d/scale` 改回 `1.0` 就行。

**材质**：`_harden_materials()` 除了设置采样和 alpha 抗锯齿，还会把
`TRANSPARENCY_ALPHA` 统一换成 `TRANSPARENCY_ALPHA_SCISSOR`（阈值 0.5）。
贴图 alpha 是二值的，scissor 的裁切结果和 alpha 混合完全一样，
但边缘能被 MSAA 抗锯齿，而且不需要深度排序、方块之间不会互相串色。

**TAA 与透明窗口互斥**：

上面那圈白线的成因是**方块之间的亚像素缝隙**：相邻方块面之间有道小于 1 像素的缝，
背景从缝里透出来，而 MSAA 的采样点盖不住它。TAA 靠跨帧抖动 + 累积正好能填掉 ——
放大对比图里，头发、深蓝袖子、裙摆边缘的白线在开 TAA 之后基本消失。但它有个硬条件：

| 渲染器 | TAA | 透明像素 |
| --- | --- | --- |
| mobile | 开 | 118552 —— 但 **TAA 被引擎拒绝**：<br>`TAA is only available when using the Forward+ renderer.` |
| forward_plus | 关 | 118487 |
| forward_plus | 开 | **0** ← 整个画面变成不透明 |

所以 **TAA 和"只有人物"的透明窗口没法同时要**，只能二选一。
默认选了透明那一侧：`use_taa = false`、`opaque_background = false`。

真要用 TAA：`use_taa = true` + `opaque_background = true`，
渲染器 `renderer/rendering_method` 改成 `forward_plus`（TAA 只在 Forward+ 下可用）。
此时背景变成 `background_color` 铺的浅色卡片（实测 `(0.97,0.97,0.98)`
经 filmic tonemap 后渲染成 `(0.957,0.957,0.961)`）。

### 透明背景下别用 SMAA / FXAA（实测会做出深色描边）

`screen_space_aa_mode` 有 关闭 / FXAA / SMAA 三档，SMAA 原理上是单帧后处理、
不要求不透明背景，看起来正好适合"透明 + 抗锯齿"——但它实测是**帮倒忙**的。

做法：同一机位、同一姿势在透明背景下渲染三张图，再逐通道 diff。

| 对比 | alpha 有变化的像素 | RGB 有变化的像素 | 轮廓像素平均亮度 |
| --- | --- | --- | --- |
| 关闭 vs FXAA | **0** | 9242 | 0.609 → 0.537 |
| 关闭 vs SMAA | **0** | 7430 | 0.609 → **0.454**（单点最大差 0.58） |

两件事一目了然：

- **alpha 一个像素都没动。** 屏幕空间抗锯齿只做边缘检测后混合 RGB，不碰 alpha，
  而轮廓的锯齿恰恰长在 alpha 上 —— 该磨的地方一点没磨到。
  三张图的半透明像素数完全相同（都是 1267 个），轮廓形状一个像素没变。
- **被磨暗的只有 RGB。** 轮廓外侧透明区的 RGB 是纯黑（见上文「图集边缘外扩」的实测），
  SMAA 把黑混进边缘像素，合成到桌面上就是一圈**深色描边** ——
  正好是原来那个"白色轮廓"的镜像毛病。

所以默认是**关闭**。透明窗口里唯一真正管用的抗锯齿是 **MSAA 8x + 2x 超采样**：
它们在**采样阶段**生效，会真正磨到 alpha，轮廓才会真的变平滑。

### 方块棱边上的"白色小锯齿"（两个叠加的原因）

鞋子边缘放大 10 倍，每条棱边上都挂着一串**点状白珠子**。用逐项关掉的对照实验量了
该区域亮度 > 0.5 的像素数（`tools/zoom_crop.gd` 的变体参数）：

| 配置 | 亮(>0.5)像素数 |
| --- | --- |
| 初始 | 20 |
| 关掉镜面高光 | 4 |
| 关掉镜面高光 **+ UV 内缩半 texel** | **0** |
| 关掉光照 | 0 |

两个原因叠在一起，得分别处理。

#### 原因一：UV 越界采样（真正让棱边采到亮 texel 的那个）

先排除"是不是方块之间的缝透出了背景"：把同一张透明渲染图分别合成到**深色底**和
**白底**上，那些亮点的颜色**完全不变** —— 说明它们是不透明像素，不是背景。

再查它们采的是贴图哪个 texel（`tools/uv_probe.gd` 打印每个面 UV 矩形内外各 2 个 texel）：

```
RightFoot8 右边: -1(92,45)a=0.00 rgb=0.57,0.60,0.76  →  +0(93,45)a=1.00 rgb=0.95,0.91,0.95  ← 白袜子
RightFoot7 左边: -1(74,61)a=1.00 rgb=0.10,0.13,0.31  →  +1(72,61)a=1.00 rgb=0.95,0.84,0.90  ← 亮色
RightFoot6 上边:  ±0(72,30)a=1.00 rgb=0.15,0.15,0.15 →  +1(72,29)a=1.00 rgb=0.91,0.82,0.82  ← 浅色条纹
```

**这张 256×256 的图集里，不同部件是紧挨着排的**：鞋面（深色 `rgb≈0.11`）的 UV 矩形
右边 1 个 texel 就是白袜子，上方 2 个 texel 就是浅色条纹。而面片的 UV 正好压在 texel
边界上，**MSAA 的着色又是按像素中心求值的** —— 边缘像素的像素中心可能落在三角形之外，
插值出来的 UV 就越过矩形边界，一越界采到的就是隔壁的亮 texel。

这也解释了它为什么对 TAA / SMAA / FXAA / MSAA / 超采样全都无感：那些都作用在
**覆盖率或时间累积**上，而这个问题出在 **UV 采样位置**上。

**修法**：`_inset_uvs()` 把每个面的 UV 朝自己的 UV 包围盒中心收缩半个 texel
（`uv_inset_texels`，默认 0.5），边缘像素就永远停在本面最外那一排 texel 之内。
纹理内容几乎不变（只有最外一小条 texel 的映射被压掉）。

> 实现细节：一个方块面拆成的两个三角形各自都含该矩形的 3 个角，所以两者的 UV 包围盒
> **完全相同**，共享的那条对角边会算出同样的结果 —— 不会在面中间撕出一条缝。

#### 原因二：镜面高光把这些亮 texel 又"点亮"了一遍

导入后的材质是 `specular_mode = Schlick-GGX` + `metallic_specular = 0.5`（实测），
Fresnel 在**掠射角**趋近 1；而方块模型的每条棱边恰好都是掠射角，于是整圈棱边都被
反射的环境光加亮。修 UV 之前那些亮点的颜色是 `rgb≈(0.85,0.85,0.94)`，
正好等于环境光色 `(0.86,0.9,1)`。

**修法**：`_harden_materials()` 里 `specular_mode = SPECULAR_DISABLED`
（`disable_specular` 开关，默认开）。像素画本来就是无高光的平面着色。

> 两个开关都能在检查器里关掉做对比：`disable_specular` 立即生效，
> `uv_inset_texels` 是启动时生效的，改了要重启。

### "extra 做一半就回到静止动画"：动画自带一段静止尾巴

现象：宠物播 `extra` 时，动作做到一半就像回到静止姿势了。

先排除"状态机把它切走了"这个方向。`tools/probe_watch.gd` 让宠物以高频动作模式
跑了 130 秒（只缩短等待时间，计时机制一个字没改），**77 次切换里
"上一个动画没播完就被切走" 0 次** —— 状态机是干净的。另外单独验过
"打断一个动作会不会补发 `finished` 信号"（`tools/probe_interrupt.gd`）：不会。

真正的原因在动画数据里。`tools/probe_pose_curve.gd` 用"两帧之间动得最厉害的那个
节点位移了多少"（取最大值，不用平均 —— 一个挥手只有几个节点在动，平均会被大量
静止节点稀释成 0）量出每个动作**真正做到哪一刻**：

| 动画 | 长度 | 动作实际做到 |
| --- | --- | --- |
| extra0 / extra4 | 1.50s | 70% |
| extra5 | 1.00s | 72% |
| extra2 / extra3 | 1.50s | 82% / 85% |
| extra6 | 1.25s | 100% |
| extra7 | 7.50s | 100% |

也就是说这些 extra **做完手势就回到站立姿势空转**，后面那段其实没在动。
而计时按动画全长算，宠物就会在那儿杵着等 —— 看着正是"做一半又回到静止动画"。

**修法**：启动时逐个量出动作结束时刻（`_measure_action_ends()`），一次性动作的计时
用它而不是全长（`action_tail_trim`，默认开）。实测 `extra0` 的动作计时
**2.49s → 1.85s**（它的手势 1.5s 就做完了），动作演完就接下一个，不再空等。

判据细节：单步位移要同时超过**绝对下限**（1.5 厘米）和**本动作峰值的 15%**。
只用一个都不行 —— 只用绝对下限时，静止尾巴上那点回正残留会被当成"还在动"，
结果只裁到 83%（等于没修）；只用峰值比例时，遇到本来就很轻的动作会把整段判成没动。

> 改完之后的状态机行为：动作计时到期会主动切到下一个动作，此时**切点在静止尾巴里**
> （`extra0` 在 1.84s 处切走，而它的手势 1.5s 就结束了），这是有意为之。
> 想恢复"按全长等完"就把 `action_tail_trim` 关掉。

### "行走时不播走路/跑步动画"：一个状态卡死 bug + 走跑分离

先说结论：**移动路径本身没有问题** —— `tools/probe_watch.gd` 让宠物只走路/跑步跑
90 秒（`-- 90 0` 把 `emote_chance` 设成 0），16 次移动**每一次都真正调用了动画**
（0 次被 `_play` 跳过），31 次切换 0 次被切走。

真凶在**点击路径**上：走路中点一下角色（几乎不动鼠标），`_begin_drag()` 会把
`_state` 设成 `DRAG` 并播 `jump`；松开时 `_end_drag()` → `_react_click()`，
如果正好落在**摸头冷却**（`pet_cooldown`）里，旧代码直接 `return`，
**没人把 `_state` 从 `DRAG` 拉回来**。后果是连锁的：

- `_begin_move()` 只在 `IDLE` 状态触发 → 从此**永远不再走路/跑步/做表情**；
- `_on_main_finished()` 又被 `DRAG` 守护挡住 → 动画换不回去，
  宠物**僵在 `jump` 的最后一帧**。

外观正是"该走的时候不播走路动画"。修法：冷却分支里把状态拉回 `IDLE`。
`tools/probe_drag_state.gd` 复现并验证了修复 —— 修复前第二次点击后 `_state` 永远
卡在 `DRAG`，修复后 3 秒内宠物恢复自己走路（`state=WALK`，动画=`walk`）。

**走跑分离**：原来走路和跑步共用一个 `move_duration`，现在拆开：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `walk_duration` | (2.0, 6.0) | 一次走路持续多久（秒） |
| `run_duration` | (1.0, 2.5) | 一次跑步持续多久；跑步费劲，默认更短促 |
| `run_chance` | 0.22 | 一次移动是跑步的概率（原有，不变） |

### "走着走着突然变成静止姿势在滑行"：两层自愈兜底

这个症状是"窗口在平移（WALK 状态）、动画却是静止的"。给状态机加了**两层自愈**，
不管根因是哪条路径，症状都会在一帧内被纠正：

1. **`_ensure_walk_anim()`**：每帧在 WALK 分支里检查"动画必须是 walk/run"，
   不对就立刻纠正（debug 构建会打印一条 `走路中动画跑偏` 便于追查是谁改的）。
2. **`_on_main_finished()` 的循环修复**：正常情况下 walk/run 是循环动画、永远不会
   `finished`；走路中收到 `finished` 就说明循环丢了 —— 补回 `LOOP_LINEAR` 并重新播放，
   否则动画会僵在最后一帧而窗口继续平移。

写自愈时踩了一个值得记的坑：第一版把它放在 `_step_move()` **之后**，而
`_step_move` 结尾可能调 `_start_idle()` 把状态改成 IDLE、动画改成 `__pet_idle` ——
自愈拿着过期的 WALK 假设又把动画改回 walk，两者打架（探针实测待机只活了 0.04 秒）。
所以自愈必须在 `_step_move` **之前**，并且守护里显式确认 `_state == State.WALK`。

> 顺带说明：100 秒真实配比（`emote_chance=0.3`）的自动观察里，状态机本身没有产生过
> "WALK + 静止动画"（44 次切换全部一致）。所以如果还看到这个症状，最可疑的是
> **拖拽路径**：宠物走到光标下时点了一下角色 → 进入 DRAG 播 `jump`（0.5 秒后停在
> 末帧）→ 窗口跟随鼠标 = 平移。这两层自愈对 DRAG 不生效（那是刻意的拖拽行为）。

**真正的根因后来找到了：眨眼动画覆盖全身。**
两层自愈上线后症状仍在 —— 因为自愈盯着的是"主 player 在播什么"，而毛病出在
**第二个 AnimationPlayer（眨眼叠加层）** 上。实测 `BlinkEye` / `BlinkTwo` 各有
**39 条轨道，和 `walk` 的轨道集合一模一样**（Root、四肢、裙子全有），只是身体部分的
键值恰好是站立姿势。眨眼在任何状态下都会随机触发（平均 7 秒一次），叠加层在场景树里
排在主 player 后面、同节点冲突它赢 —— 于是走路途中一眨眼，全身被钉成站立姿势
0.7~1.1 秒，窗口却照常平移。这正是"突然变成静止动画并且平移"。

修法：`_scan_animations()` 把眨眼动画拷进叠加层时，`_strip_to_face()` 只保留
`/Face/` 下的轨道（眼皮 / 眉毛 / wink，实测裁到 14 条），身体继续由主 player 驱动。
注意必须 `duplicate()` 再裁，否则会把主库里共享的同一份动画资源也裁掉。
验证见 `tools/probe_blink_walk.gd`：修复后眨眼期间腿部活动帧 84/90（与基准一致），
修复前的完整版对照只有 47/90 且带一次 0.17 的猛 snap。

### 鼠标穿透会让窗口整体"提亮"

这个坑值得单独记一笔。`window_set_mouse_passthrough()` 在 Windows 上是靠
**`SetWindowRgn` 裁剪窗口区域**实现的，实测副作用是：**被裁出来的可见区域
整体会多一层很淡的提亮**，桌面图标看着发白，而且提亮的边界正好落在角色轮廓上
—— 很容易被误判成"背景被光照照亮了"（跟光照没有任何关系）。

同一块屏幕区域，运行中 vs 关闭后的平均像素差：

| | 角色轮廓内 | 轮廓外 |
| --- | --- | --- |
| 开穿透 | 明显提亮（+8 ~ +10 / 255） | 精确 0.00 |
| **关穿透** | **干净** | 精确 0.00 |

所以 `mouse_passthrough_enabled` 默认是 **false**：
"背景绝对干净" 和 "空白处能点到后面的窗口" 只能二选一。

### 导出版"发白发灰"的真相（之前那份结论是错的）

**旧结论（错）**：以为"导出的 exe 无法启用 Windows 窗口透明"。
**真实原因**：**背景色的 RGB 没被清零**，被 DWM 当成预乘 alpha 数据**加**在了桌面上。

透明 viewport 里，清屏色/背景色的 **alpha 会被置 0，但 RGB 会原样保留**。
于是窗口帧缓冲变成"alpha=0 而 RGB≠0"，而 DWM 是按预乘 alpha 合成的 ——
等价于把那点 RGB **加到**桌面上，表现就是整块均匀发白/发灰。

判定依据（同一像素，开/关宠物窗口对比，同时抓一块远离窗口的对照区）：

| | 有宠物 | 无宠物 | 差 |
| --- | --- | --- | --- |
| 修之前 | 183,183,199 | 30,30,46 | **+153**（≈ sRGB(0.3)，正是不透明的默认清屏色） |
| 修之后（导出） | 66,66,82 | 30,30,46 | **+36** |
| 修之后（`--path`） | 66,66,82 | 30,30,46 | **+36** |
| 对照区（远离窗口） | 24 | 24 | **0** |

两个要点：

- 差值**恒定、不随底色变化**。如果只是"半透明叠加"，差值会随底色变；
  恒定说明是**加法混合**，而不是"窗口没拿到透明"。
- 修完之后**导出版和 `--path` 完全一致**（都是 +36）。这个 +36 是两种模式都有的基线，
  不是导出版特有的，也就说明导出版的透明已经正常了。

**修法**：`project.godot` 里加一行

```
environment/defaults/default_clear_color=Color(0, 0, 0, 0)
```

透明模式下 `_apply_background()` 还会顺手把 `env.background_color` 也清成全透明，双保险。

> **最终结论（根因已定位）**：这是 **Vulkan 后端（Forward+ / Mobile）在透明窗口下写出的帧缓冲
> 没有做预乘 alpha** —— 背景的 RGB 原样保留、alpha 却是 0，而 DWM 按预乘 alpha 合成，
> 等价于把那点 RGB **加到**桌面上，于是出现那层白。
>
> **换成 Compatibility（OpenGL）渲染器后彻底消失**：同一个位置，开/关宠物窗口的像素差
> 从 `+36,36,36` 变成 **`0,0,0`**。
>
> ```ini
> renderer/rendering_method="gl_compatibility"
> ```
>
> 同一场景、固定姿势下两种后端的对照（`tools/shot_alpha.gd` + `tools/measure_alpha_edge.gd`）：
>
> | | Vulkan (Forward+ / Mobile) | OpenGL (Compatibility) |
> | --- | --- | --- |
> | 不透明 / 全透明 | 35486 / 118347 | 35496 / 118228 |
> | 轮廓半透明像素 | 820 个 | 817 个 |
> | **轮廓像素平均亮度** | **0.609**（未预乘，偏亮） | **0.261**（已预乘，正确） |
>
> 像素数量基本一致，说明 MSAA + alpha scissor 照常生效；亮度比约等于平均覆盖率，
> 正是"有没有预乘 alpha"的差别 —— 顺带也解释了轮廓上那圈偏亮的白边。
>
> 逐项试过、**都不是**原因：Forward+ / Mobile 之间切换、MSAA 开关、2x 超采样开关、
> `background_mode`（`BG_CANVAS` / `BG_CLEAR_COLOR`）、把清屏色压到 0.001、
> 以及 `xr/shaders/enabled`（那是 VR 用的，和这个无关，已移除）。

> 顺带删掉了之前那段"导出版强制切不透明卡片"的逻辑（`OS.has_feature("template")`）——
> 它是基于错误结论加的，留着反而会让导出版莫名其妙变成一张白卡片。

> **Camera3D 自己挂了 `environment` 时会覆盖 WorldEnvironment**，只改 `$WorldEnvironment`
> 是不生效的。`_apply_background()` 现在改的是**真正生效的那个**
> （`_effective_environment()`：相机上挂了就用相机的）。

### 导出成 exe（分发 / 独立运行）

流程就是 `项目 → 导出 → Windows Desktop`，预设和导出模板都已就绪，**不用改任何开关**。

透明形态在编辑器里和导出版里表现一致（见上一节），所以直接导出即可。
`opaque_background = true` 时才会走卡片形态，卡片底色由 `background_color` 控制。

#### 导出时的两个坑

1. **当前预设是 `binary_format/embed_pck=false`**，产物是 **`wi.exe` + `wi.pck` 两个文件**，
   分发时必须一起拷贝，只给 exe 是打不开的。想只发一个文件就在导出面板里勾上
   **Embed PCK**。
2. **测导出版之前先关掉编辑器的嵌入窗口模式**（`编辑器设置 → Run → Window Placement`
   → Embed Game Window），否则看到的还是编辑器里的画面，透明、弹窗位置都不作数。

### 图集边缘外扩（dilate）

Blockbench 的皮肤图集是一堆 UV 岛拼在一张 256×256 的图上，岛与岛之间是空白像素。
把这张图量了一遍：

| | |
| --- | --- |
| 完全不透明 | 20600 texel（31.4%） |
| 完全透明 | 44936 texel（68.6%） |
| 半透明 | 0（alpha 只有 0 和 1 两种） |
| **紧贴图案那圈透明 texel 的平均 RGB** | **(0.000, 0.000, 0.000)** |

**空白是纯黑的，不是白色。** 所以 UV 越界采样混进来的是黑 ——
表现是**一圈偏暗的描边**，不是白边。（这也和渲染数据对得上：
轮廓过渡像素亮度 0.573，比实体像素的 0.712 还暗。）

`_harden_materials()` 里加了运行时外扩：`_dilate_image()` 把不透明像素的 RGB
往相邻透明像素复制，**alpha 保持 0**。这样越界采到的是相邻图案的颜色，
同时 alpha scissor 的裁切位置完全不变（图案不会"长胖"）。
参数是 `dilate_pixels`，默认 2，设 0 即关闭。

实测（同机位，"边缘像素平均亮度 / 实体像素平均亮度"）：

| `dilate_pixels` | 边缘/实体 |
| --- | --- |
| 0（关闭） | 0.757 |
| **1** | **0.771** |
| 2（默认） | 0.771 |
| 4 | 0.770 |

**1px 就已经饱和** —— 因为用的是最近邻采样、UV 精确压在 texel 边界上，
真正会越界的边界像素本来就不多。所以这是个"便宜但收益有限"的保险，
默认给 2px 是为了将来万一改成线性采样或者开 mipmap 时 padding 够用。

**为什么在运行时做，而不是直接改那张 PNG**：`peekdeek_opt.glb` 的贴图是
**内嵌**在 glb 里的（`gltf_to_glb.mjs` 从 `src.images[].bufferView` 复制过去），
Godot 导入 glb 时把它提取成 `peekdeek_opt_0.png` —— 直接改这个文件会在
glb 重新导入时被覆盖。真要落到资产上，得改 `gltf_to_glb.mjs`（Node 侧做 PNG
解码/外扩/重编码）。

### "白色轮廓"的排查结论

按现在的配置渲染，再把透明图按预乘 alpha 合成到深色底、放大 3~4 倍看，轮廓是干净的：

- 全透明区域的 RGB 实测全是 **(0,0,0)**，没有底色被混进来；
- 轮廓过渡像素的平均亮度 **0.573**，比实体像素的 **0.712** 还**暗** ——
  说明它们是"模型色 × 覆盖率"的正常过渡，不是被掺了白色。

也做过四联对照实验（当前配置 / 关高光 / 关超采样 / 关 MSAA，同一机位放大 3 倍），
四种情况都没有出现白色描边，所以白边不是高光或 MSAA 造成的。

**这种情况下最可能是超采样那层偏亮的过渡带**（已经关掉），其次要怀疑的是
显示器/显卡驱动的锐化，以及**看错了地方**——编辑器 3D 视口有它自己独立的
背景与抗锯齿设置，和运行时的效果不是一回事。

### 如果你还看到白边

0. 先确认你看的是**运行中的游戏窗口**，不是 Godot 编辑器的 3D 视口 ——
   编辑器视口有独立的一套背景/抗锯齿设置，和最终效果不是一回事
1. **确认重启了应用** —— 贴图导入参数是导入期生效的，光重启窗口不够，
   必要时删掉 `.godot/imported/peekdeek_opt_0*` 再让 Godot 重新导入一次
2. 检查是不是**显示器/显卡驱动的锐化**（NVIDIA 控制面板的"图像锐化"、
   AMD 的"Radeon Image Sharpening"）在深色桌面上放大了边缘对比
3. `desktop_pet.gd` 里有个 `texture_filter_mode` 参数，默认最近邻，
   想换线性可以直接在检查器里改
4. 如果看到的是**深色**描边（不是白的）—— 先看 `screen_space_aa_mode` 是不是被打开了。
   SMAA / FXAA 在透明背景下会给轮廓掺黑（见上文那一节），调回「关闭」即可

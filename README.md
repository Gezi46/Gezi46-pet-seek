# PeekDeek 🐾

> 名字来自 `peek`（她会偷看你的屏幕）+ `deek`。中文里平时就叫她**桌宠** —— 那是类别词，
> 不是项目名。
>
> ⚠️ **别只改 `project.godot` 的 `config/name`**：那会让 `user://` 指向新的数据目录，
> 她的长期记忆 / 配置 / 密钥会全部"失联"（`app_userdata` 下那些旧目录就是这么来的）。
> 项目用 `use_custom_user_dir` 把数据目录钉在原处，改名请连那两行一起看。

一个用 **Godot 4.7** 做的 3D 桌面宠物：无边框置顶小窗口里站着一位 Blockbench 蓝发女仆，
会在屏幕上自己散步、偶尔跑两步，可以拖着走、摸摸头。

**GPL-3.0 开源**（见 [`LICENSE`](LICENSE)）—— 可以自由使用、修改、再分发（含商用），
但**衍生作品也必须以 GPL 开源**并保留版权声明。项目名与美术资产**不随代码授权**，
见 [`TRADEMARK.md`](TRADEMARK.md)。


> **要改代码先看这两样**：`CONVENTIONS.md`（**代码宪法** —— 文件上限 / 分区与索引 /
> 模块边界 / GDScript 写法 / 验证阶梯 / 密钥规矩）。
>
> 想一眼看清 20 个脚本各自管什么、哪个文件超了 500 行该拆：
> ```
> godot --headless --path . --script res://tools/probe_map.gd
> ```

窗口有两种形态，由 `opaque_background` 一个开关决定，三种跑法（编辑器 F5 / `启动桌宠.bat` / 导出的 exe）表现一致：

| 形态 | 桌面上的样子 | 什么时候是这种 | 抗锯齿 |
| --- | --- | --- | --- |
| **透明**（默认） | 只有人物，其余完全透明 | 编辑器 F5、`启动桌宠.bat`、导出的 exe 都一样 | MSAA 8x + 2x 超采样 |
| 不透明卡片 | 一块 330×470 的浅色卡片 | 手动把 `opaque_background` 打开 | 同上，另外可选 TAA |

以前导出版会单独发白，那是清屏色没清零造成的（已修，见下文
「导出版"发白发灰"的真相」），现在两种启动方式表现一致。

## 两个 .bat：跑起来看 / 一条命令做检查

都在项目根目录，双击即可：

| 文件 | 作用 |
| --- | --- |
| `启动桌宠.bat` | 直接跑起来看。等同于编辑器 F5，只是不用开编辑器 |
| `检查效果.bat` | 一条命令跑完静态检查：渲染固定取景 → 存到 `检查输出/`，并在控制台打印可对比的数字 |

`检查效果.bat` 调的是 `tools/check_effect.gd`。它把"当前配置"和"打开高光的参照"
放在**同一个引擎进程**里各渲染一遍 —— 每个变体都得重新实例化宠物（`uv_inset_texels`
之类是 `_ready` 里生效的），而拉起一次引擎要 5~10 秒，一个个单开进程一轮就得 40 秒起。

它同时会做一致性校验：两个变体的**实心像素数**应该几乎相同（差异 >5% 就报警），
因为"几何被改坏"正是最需要早点发现的事。

> **它能查什么、不能查什么**：模型有没有渲染出来、几何有没有被改坏、两次跑是否同一个姿势
> —— 这些它靠得住（姿势是显式钉死的，靠"等 N 帧"会被帧长抖动带偏，实测能差 22%）。
> 但**"白边"这类毛病它查不出来**：掠射角高光依赖视角，固定正脸姿势下连参照组都复现不出，
> 所以报告在参照组没有明显更脏时会直接说"别据此判断"，而不是给出假的通过结论。

模型和动画来自本项目原有的 `peekdeek.gltf`，已做了一轮优化（见下文）。

## 快速开始

用 Godot 4.7 打开这个文件夹，直接按 **F5**（主场景已设为 `scenes/pet.tscn`）。

> **首次打开会先导入资源**（约 10-30 秒 —— `peekdeek.gltf` 那个 3D 模型要转一遍）。
> 导入完成前直接启动会报一屏 `referenced non-existent resource`，那**不是代码问题**。
> 用编辑器打开一次、或跑一次 `--import` 就好了。`.godot/` 是导入缓存，**不进版本库**。

命令行启动：

```powershell
# 把第一段换成你自己的 Godot 4 可执行文件路径；第二段就是本项目目录
# 首次先建导入缓存（已经跑过一次就不用加这行）
& "C:\Godot\godot.exe" --headless --path . --import
& "C:\Godot\godot.exe" --path .
```

`启动桌宠.bat` 已经自动处理了这一步（检测到没有 `.godot\imported` 就先导入一次）。

## 聊天与 AI（接 deepseek-web-api）

她的嘴可以接在本机的 **deepseek-web-api** 上 —— 它把
DeepSeek 网页版（chat.deepseek.com）包成**本地 OpenAI 兼容接口**，所以只要浏览器
登录过网页端、把 userToken 填进它的管理页就行，**不需要官方开放的 API Key**。
服务在跑就是真回话，**服务没起就退回本地台词**，不会报错、也不会把窗口卡住。

**两个后端随便切**，菜单「聊天与 AI」→「AI 服务设置…」里选一下来源就自动填好地址和模型
（选完还能手改）。两个都是 OpenAI 兼容协议，桌宠只换地址/密钥/模型名：

| 来源 | 地址 | 文本模型 | 视觉模型 | 要钱吗 |
| --- | --- | --- | --- | --- |
| **官方 API**（当前默认） | `https://api.deepseek.com` | `deepseek-flash` | `deepseek-v4-flash-vision-exp` | 要（付费 key） |
| 本地网页版 | `http://127.0.0.1:8520/v1` | `deepseek-chat` | 无（看不到图） | 不要，但要网页端 userToken 不过期 |

| 项 | 说明 |
| --- | --- |
| 鉴权 | `Authorization: Bearer <key>`（官方填 `sk-` 开头的付费 key；本地填管理页第 ② 栏那串） |
| 协议 | `POST {base}/chat/completions`，SSE 分片走 `choices[0].delta.content`，收尾 `data: [DONE]` |
| 探活 | `GET {base}/models` —— **故意不用 `/healthz`**：那是本地代理专有的，官方 API 上会 404，会被误判成"服务没起来"然后永远退回本地台词（踩过） |
| 密钥存哪 | 菜单里填的会存进 `user://pet_chat.cfg`（用户目录，不进项目、不会被误提交） |

> 官方 API 实测：`deepseek-flash` 回文本会**带 `reasoning_content`**，
> 而流式分片里它经常是 **`null`** —— GDScript 的 `String(null)` 会直接抛
> `Nonexistent 'String' constructor` 把整条流打崩，所以取值必须先判类型
> （`_as_text()`）。这个坑也是实测踩出来的。

### 偷看屏幕 / 看摄像头：走**视觉那条独立链路**

这两个功能都要"看图说话"，所以它们**不走文本那个客户端**，而是走另一条：
`vision_url` + `vision_model` + 同一个 key（`vision_access_key` 留空就复用文本的）。
独立客户端 = 独立连接，所以她正在说话时照样能截屏去问，两张图也不会互相排队。

| 功能 | 图从哪来 | 怎么触发 |
| --- | --- | --- |
| **偷看屏幕** | `DisplayServer.screen_get_image()` → 缩到 1280 宽 → JPEG → data URL | 菜单「偷看屏幕看看」/ 打开「定时偷看屏幕」后每 `peek_every_min` 分钟一次 |
| **看摄像头** | **Godot 自带的 CameraServer** 采集（不依赖 AIGirlfriend 等外部程序） | 菜单「看一眼摄像头」/ 打开「定时看摄像头」后每 `camera_every_min` 分钟一次 |

**主动说话也会"先瞥一眼"（默认开）**：她自己找话题时，按 `proactive_peek_chance`（默认 0.35）
的**概率**先抓一张屏幕，拿着画面（以及"主人前台开着什么窗口"）说话 —— 不然她只能凭**记忆**
起话头，而记忆是过去的事，主动开口就容易"和主人正在干的事不一样"（2026-09-27 用户报的问题）。
菜单「主动说话时先看一眼屏幕」可以关掉；概率在检查器里调（`0` = 从不，`1` = 每次都看）。

抓到的图 **只在那一轮**发给模型 ✓ —— 它**不进对话历史**（`pet_chat.gd` 写历史时只存纯文字），
也没有任何"上次那张图"的缓存 ✓。所以她之后还提那件事，是因为那次偷看**写进了一条文字记忆**
（"她看屏幕时看到：…"），而不是图片被反复喂回去。

**抓不到的情况**（2026-09-27 实测，成因写在 `pet_peek.gd` 的 `PROMPT_PEEK` 注释里）。
抓屏走的是**桌面合成**这一层，所以有两类画面它看不到：

1. **独占全屏**（Exclusive Fullscreen）的游戏 —— 它不进桌面合成，抓到的只有桌面；
2. **带反作弊**的游戏（实测《某个游戏》+ 腾讯 ACE）—— 反作弊会**主动屏蔽截屏**，
   这是它的设计目标，不是 bug。

这种情况她只会拿到一张桌面 ✗，所以提示词里明确要求她"**只说你真看到的，别猜主人在玩什么**"
—— 她会如实问一句"你在忙什么呢"✓，而不是把桌面硬说成某个软件 ✗。
想让她真看到：把游戏改成**无边框窗口**（独占全屏那条就能解决 ✓；反作弊那条改不掉 ✗）。

实测（`tools/probe_vision.gd`，会真的抓当前屏幕发给视觉模型）：

```
B 截图 data URL = 160587 字节（约 117 KB）
C 用时 3.0s
C 回复：主人又在熬夜捣鼓代码啦，我看到Godot引擎和AI窗口了，是不是又卡在什么bug上头疼呢？
PROBE_VISION OK
```

**摄像头的两个坑**（都写进代码注释了）：

1. **必须先 `CameraServer.set_monitoring_feeds(true)`** —— 不调的话 `get_feed_count()`
   恒返回 0 并报 `not actively monitoring feeds`；
2. 摄像头刚打开时纹理要晚几帧才有内容，所以要等（最多约 5 秒），拿不到就认输。
   本机**没有摄像头**，实测走的是"优雅失败"这条：`_camera_shot()` 安静返回空串，
   她回一句「我这边没找到摄像头诶…」（`tools/probe_camera.gd` 验的）。
3. `_camera_look()` 是**协程**（要 await 等帧），所以 `_check_camera()` 里**故意不 await**
   —— 那条链跑在 `_process` 上，在那儿 await 会让本帧提前返回、状态机被重入。

> 本地网页版那条链路看不到图（它只把 messages 拼成文本），所以"来源"选本地版时
> 视觉模型留空即可，这两个功能会自动提示"还没配好看图的模型"。

### 令牌过期是这个链路最常见的故障

网页端 userToken 会随登录态过期（通常几天到几周）。过期后上游返回 `40003`，而
deepseek-web-api 会把这段错误**当成正文**吐出来。桌宠这边特意识别了它：整段以
`[代理错误]` 开头（**前面常带几个换行**，所以判断前要先去掉空白 —— 这点踩过坑，
不带 strip 就匹配不上，报错会被当回复念出来），识别到就换成一句
"去管理页重新粘贴 userToken"，`tools/probe_chat_stream.gd` 的 E 段专测这条。

修法是纯操作：打开 <http://127.0.0.1:8520/admin> 重新粘贴 userToken，代码侧不用动。

### 怎么开始聊

| 操作 | 效果 |
| --- | --- |
| **双击角色** | 弹出底部输入框，打完字回车发出去 |
| 右键 →「聊天与 AI」→「打开聊天框」 | 同上 |
| 右键 →「聊天与 AI」→「让她想个话题」 | 不等你开口，她自己找个话题说一句 |
| 右键 →「聊天与 AI」→「偷看屏幕看看」 | 截当前屏幕发给她（**现在看不到画面**，见下） |
| 右键 →「聊天与 AI」→「看一眼摄像头」 | 让 AIGirlfriend 用摄像头拍一张并评论（另一条链路，见下） |
| 右键 →「聊天与 AI」→「主动说话」☑ | 定时主动搭话的总开关 |
| 右键 →「聊天与 AI」→「定时偷看屏幕」☑ | 定时截屏那条链路的开关（默认关） |
| 右键 →「聊天与 AI」→「定时看摄像头」☑ | 摄像头那条链路的开关 |
| 右键 →「聊天与 AI」→「AI 服务设置…」 | **改后端地址 / 密钥 / 模型**，存盘并立刻重连 |
| 右键 →「聊天与 AI」→「重新连接 AI 服务」 | 服务刚起来、或改完设置想立刻重试时用 |
| **Esc** / 点面板外面 | 关掉输入框或设置面板 |

三个勾选项点一下立刻翻转，气泡里回一句「xxx：开 / 关」，并写进
`user://pet_chat.cfg` —— 下次启动还是这个状态。

回复是**流式**的：服务端的 token 一个个到，气泡就一个字一个字往外冒，说完再淡出。
输入框上方常驻最近几行聊天记录（`chat_log_lines`）。

### 参数（检查器分组「聊天」）

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `chat_enabled` | true | 总开关。关掉 = 完全不联网，回到纯本地桌宠 |
| `chat_url` | `http://127.0.0.1:8520/v1` | AI 服务地址（deepseek-web-api 的 OpenAI 兼容入口） |
| `chat_access_key` | `sk-ds-...` | 本地访问密钥（管理页第 ② 栏；也可直接填 userToken） |
| `chat_model` | `deepseek-chat` | 模型名。想要深度思考换成 `deepseek-reasoner` |
| `chat_system_prompt` | **空** | 额外要求。她的**人设本身**在 `scripts/ai/pet_persona.gd` 里（18 岁、刚高中毕业）；这里填的东西会作为"主人的额外要求"追加到人设后面，填空就只用人设 |
| `chat_persona_name` | `小蓝` | 她的名字（写进人设） |
| `hibernate_when_offline` | true | 联系不上 AI 服务时她进**假死**：只剩基础功能（见下文「离线假死」）。关掉 = 断网时她照旧装作没事 |
| `memory_enabled` | true | 长期记忆总开关（`scripts/ai/pet_memory.gd`）。关掉 = 她每次都像第一次见你 |
| `memory_ai_extract` | true | 让她用模型抽记忆。会多一次非流式请求（很便宜但确实在花钱）；关掉只影响自动抽取，本地规则的记忆照常 |
| `memory_ai_every_sec` | 30 | 两次 AI 抽取之间的最小间隔（防止连发几句就连着调模型） |
| `memory_summary_every` | 6 | 每几轮更新一次"工作记忆"（整体了解 + 待跟进话题 + 最近情绪） |
| `memory_observe` | true | 把"主动搭话 / 偷看屏幕"说的内容也选择性记进长期记忆（关掉只记打字聊的那些） |
| `chat_log_lines` | 3 | 输入框上方显示几行聊天记录 |
| `proactive_enabled` | true | **开局默认值**，之后由菜单「主动说话」切换并存盘 |
| `self_talk_enabled` | true | 太久没人理她就自己找话说（只在检查器里改） |
| `self_talk_after` | (300, 900) | 安静多少秒之后主动开口（随机区间）。**"普通"档的基准** —— 其余三档按它缩放，菜单「主动说话的频率」里选 |
| `peek_enabled` | **false** | **开局默认值**，之后由菜单「定时偷看屏幕」切换并存盘；见下 |
| `peek_every_min` | 5.0 | 偷看的间隔（分钟） |
| `camera_look_enabled` | **false** | **开局默认值**，之后由菜单「定时看摄像头」切换并存盘 |
| `camera_look_url` | `http://127.0.0.1:8777` | AIGirlfriend 的地址（`AIGirlfriend.exe --serve` 的默认端口） |

> **地址 / 密钥 / 模型这三项会写进存档**（`user://pet_chat.cfg` 的 `[ai]` 段），
> 因为它们现在可以在菜单里改 —— 改完立刻重连，不用重启。其余开关同理。
> 存档里**缺键**时落回检查器里的值 —— 老存档不会把新加的开关静默关掉。

### 两种"她主动开口"的来源

换到 deepseek-web-api 之后只剩两条，**因为服务端没有推送通道** ——
原来那套 `GET /api/proactive/{user_id}/pending` 轮询已经删掉了。

1. **桌宠自己计时**：`self_talk_after` 时间到、且没人在跟她互动，就发一句提示词
   （`PROMPT_PROACTIVE`）让模型找话题。菜单里「让她想个话题」是同一路，只是手动触发
   ——**手动那条不受开关限制**（你明确让她说，她就说）。
2. **偷看屏幕后评论**：菜单「定时偷看屏幕」打开后每 `peek_every_min` 分钟截一次屏。

> 两条都受菜单「主动说话」管（第 2 条还要开它自己的开关）。

> ⚠️ **偷看屏幕现在拿不到画面**：deepseek-web-api 只把 `messages` 拼成一段**文本**
> 交给网页端，图片不会被真正看到。桌宠仍然按 OpenAI 的多模态格式发
> （`image_url` 那条），但服务端用不上 —— 所以这条链路实际只发过去文字提示。
> 默认关着，等哪天服务端支持了图再打开就有意义。

### 两个「看」是两条不同的链路

| 菜单项 | 看什么 | 走哪儿 | 要不要额外开东西 |
| --- | --- | --- | --- |
| 让她看看我在干嘛 | 屏幕（`screen_get_image` → JPEG → data URL） | 视觉模型（`vision_url` / `vision_model`） | 模型得是多模态的 |
| 看看我这边（摄像头） | 现实（`CameraServer` 抓一帧 → JPEG） | 同上，也是视觉模型 | 机器上得有个 Godot 能枚举到的摄像头，见下 |

### 摄像头识别不到时怎么查（本机实测过的一例）

**先说结论：Windows 上用不了。** 不是相机的问题，也不是权限问题 ——
**官方 Godot 的 Windows 构建里没有摄像头后端**，`CameraServer` 只是个空壳 API。

直接证据是在二进制里找符号（用同一套方法找 `CameraServer` / `CameraFeed` / `wasapi`
都能找到，说明方法可靠）：

| 字符串 | 4.7 Steam tools | 4.6 官方标准版 |
| --- | --- | --- |
| `CameraServer` / `CameraFeed` | ✓ 有 | ✓ 有 |
| `mfplat` / `MFStartup` / `MFEnumDeviceSources` / `MF_DEVSOURCE` | ✗ **一个都没有** | ✗ **一个都没有** |

Media Foundation 是 Windows 上抓摄像头的唯一途径，它的符号不在 → 驱动没编进去。
表现完全吻合：`get_feed_count()` 恒为 0、`set_monitoring_feeds(true)` 不报错、
`--verbose` 下一个字都不提摄像头（有驱动时至少会有几行 MF 相关输出）。

**同一台机器上系统侧的一切都是好的**（都实测过，别再往这个方向查）：

| 检查 | 怎么看 | 本机结果 |
| --- | --- | --- |
| 设备在不在 | 设备管理器 → 照相机；或 `Get-PnpDevice -Class Camera` | ✓ 在，状态 OK、问题码 0 |
| 系统认不认它是采集设备 | WinRT 从普通应用视角枚举 `DeviceClass.VideoCapture` | ✓ 有 1 个 |
| 权限 | 设置 → 隐私和安全性 → 相机（含**"允许桌面应用访问相机"**） | ✓ Allow |
| 有没有被占用 | `Get-Service FrameServer`（有程序取流时是 Running） | ✓ 打开自带相机后变 Running，说明**能出流** |
| 引擎能不能枚举到 | `tools/probe_camera.gd`（**必须带窗口跑**，`--headless` 下恒为 0） | ✗ 等 8 秒还是 0 |

所以这条功能**在 Windows 上做不到**（要做得换一条采集路径，比如外部程序 ——
但那个方向的代价是引入一个后台进程，权衡下来不值得，所以没做）。

现在的行为是"优雅退化"：菜单点「看一眼摄像头」，她会说
**"唔…我这台机器上用不了摄像头诶。"** —— 不会再让人以为是相机或权限坏了。

> 采集代码在 `_camera_shot()`：它会把失败原因分开 —— "没找到设备"（枚举 0 个）、
> "设备在但取不到画面"（被占用 / 硬开关）、"压 JPEG 失败"。
> 前两种的排查方向完全不同，日志里（debug 构建）能看到具体是哪一种。

她要是说"我这边没找到摄像头诶…"，说明 `CameraServer.get_feed_count()` 是 0。
按这个顺序查（前四条是系统侧，最后一条是引擎侧）：

| 检查 | 怎么看 | 本机实测结果 |
| --- | --- | --- |
| 设备在不在 | 设备管理器 → 照相机；或 `Get-PnpDevice -Class Camera` | ✓ 在，状态 OK、问题码 0 |
| 系统认不认它是采集设备 | WinRT 从普通应用视角枚举 `DeviceClass.VideoCapture` | ✓ 有 1 个 |
| 权限 | 设置 → 隐私和安全性 → 相机：**"允许桌面应用访问相机"** 也要开（最容易漏这条） | ✓ Allow |
| 有没有被占用 | `Get-Service FrameServer` —— 有程序在用时会 Running | ✓ Stopped（没人占） |
| 引擎能不能枚举到 | `tools/probe_camera.gd`（**要带窗口跑**，`--headless` 下枚举恒为 0） | ✗ 等 8 秒还是 0 |

**本机就是最后一条过不去**：系统侧全绿，但 Godot 4.7（Steam tools）和 4.6（官方标准版）
**两个引擎都枚举到 0 个**，而且 `--verbose` 下一个字都不报 —— 所以不是你项目的问题，
是引擎的 Media Foundation 枚举和这台机器/这个相机的组合有问题。

**还能自己验一下的三件事**（任意一件有变化都值得告诉我）：

1. **打开 Windows 自带的「相机」应用**，看能不能出画面。出不了 → 问题在相机/驱动这一侧
   （笔记本上尤其常见的是**摄像头的硬开关/快捷键**把镜头断电了，设备还在、但拿不到流）；
2. 设备管理器里把相机**禁用再启用**，或者重装一次它的驱动（UVC 通用驱动）；
3. 换个 Godot 版本 / 换台有摄像头的机器跑 `tools/probe_camera.gd`。

> 采集代码在 `_camera_shot()`：它现在会把失败原因分开说 ——
> "没找到设备"（枚举 0 个）和"设备在但取不到画面"（被占用 / 硬开关）是两回事，
> 排查方向完全不同。台词也分了两种，日志里（debug 构建）能看到具体是哪一种。

这两条（加上聊天本身）**共用一个气泡**，所以互相加了闸：
一条在飞的时候点另一条，她只会回「等我先把这句说完～」，不会把正在冒的字顶掉。

两者互不影响：giftia 没起的时候摄像头那条照样能用，反过来也一样。
摄像头那条**一次性请求、不需要流式**，所以桌宠里它直接用 `HTTPRequest`
（聊天那条用不了它，原因见下），拍完把 `reply` 显示到气泡里。

> **摄像头很慢，别按 30 秒超时设**：实测抓一帧要 **31 秒 / 51 秒**（两次连拍），
> 最慢见过约 155 秒。所以桌宠那边 `_camera_req.timeout` 是 **240 秒**，
> 而且点了菜单会先把气泡撑成「让我看看…」，不让她干站着不出声。
> 另外 AIGirlfriend 的 `/api/see` 是**同步阻塞**在它那个单线程 HTTP 服务里的：
> 抓帧期间连 `/api/status` 都会超时。桌宠这边不受影响（有超时兜底），
> 但你要用浏览器调试台的话得等这一张拍完。

### 为什么聊天那条不用 HTTPRequest

`HTTPRequest` 只在请求**结束**时用 `request_completed` 一次性给出整个 body，
`get_downloaded_bytes()` 只给进度数字、拿不到内容 —— SSE 就没法边收边显示。
所以 `scripts/ai/pet_chat.gd` 用 `HTTPClient` 自己推一个状态机，每帧由主脚本的 `_process`
调 `tick()` 推进，**全程同步、不 await、不起线程**：既不阻塞渲染，也不和窗口操作打架
（`_process` 里 await 会让本帧提前返回、状态机被重入）。

里面是两条独立通道：`_sse` 跑长流式对话（一次可能 5~30 秒），
`_short` 跑探活和主动消息轮询 —— 长流占着连接时短请求才不会排队干等。

### 聊天部分的三个坑

**1. keep-alive 读完 body 后，status 会从 `STATUS_BODY` 退回 `STATUS_CONNECTED`。**
第一版状态机把它当成"刚连上"，于是**反复重发同一个请求**，而且每轮还在同一帧里
二次读 body（实测刷满 `Condition "status != STATUS_BODY"`）。现在这个分支会看 `phase`：
`CONNECTING` 才发请求，已经有响应码了就判定"这一轮收完了"。

**2. 按行切 SSE 必须按字节切。** 直接对可能以半个多字节字符结尾的 chunk 调
`get_string_from_utf8()`，截断处会被换成 `U+FFFD` 而且那几个字节**永久丢失**、拼不回来。
所以 `_drain_sse()` 是在 `PackedByteArray` 上 `find(0x0A)` 切行，只对切出来的完整行解码。
验证见 `tools/probe_chat_stream.gd` 的 A 段（故意从"你"字的第 2 个字节处切断）。

**3. `image_url.url` 得是完整的 data URL，不能只放 base64 裸串。**
giftia 原来是把 `data:image/jpeg;base64,` 前缀**切掉**再塞进 `image_url.url`，
上游直接回 `400 Unsupported image_url format` —— 因为那里要的是"一个 URL"，
要么 http(s)，要么完整的 data URL。改法见 `backend/emotion_graph.py` 的
`_build_llm_messages()`：有前缀就原样用，没有才补上。这个坑是靠
`tools/probe_chat_ui.gd` 的 F 段（真发一张截图）才暴露出来的。

### 输入框怎么拿到键盘

桌宠窗口是 `NO_FOCUS` 的，不然会抢走别的窗口焦点。双击她时先
`window_set_flag(WINDOW_FLAG_NO_FOCUS, false)` + `window_move_to_foreground()`，
关掉输入框再设回 `true`。

输入框和气泡都用 `SystemFont`（`Microsoft YaHei UI` / `Microsoft YaHei` / `SimHei`），
不指定的话 CJK 字形是空的、中文根本显示不出来。

### 流式冒字为什么不能走 `_say()`

`_say()` 自带 1.8 秒的淡出 tween。流式显示时是**直接改 `_bubble.text`**，
一个字都不经过 `_say()`；等整段回复收完（`replied` 信号）才用 `_say(完整回复)` 收尾。
否则那句淡出会在冒字途中把气泡藏掉。

### 四条链路共用一个气泡

聊天流（`_chat_streaming`）、偷看屏幕、摄像头（`_camera_busy`）、后端主动推送
都会往**同一个气泡**里写字，所以两两之间必须有闸：

- `_camera_busy` 和 `_chat_streaming` 是**两个独立的标记**，绝不互相清。
  早先 `_on_camera_look_done()` 顺手把 `_chat_streaming` 也清了 ——
  收流和摄像头一重叠就会变成"字还在冒、状态却说没在冒"，收尾判断全乱套。
- 摄像头那条起手式走 `_hold_bubble()`（掐 tween + 显示气泡，**不碰任何忙标记**），
  不是 `_begin_stream_bubble()`（那个会把 `_chat_streaming` 置真）。
- 同时点另一条只会得到一句「等我先把这句说完～」，不会把正在冒的字顶掉。

> `tools/probe_chat_ui.gd` 的 G 段专门断言过"摄像头链路不该带脏 `_chat_streaming`"，
> 顺手把上面那个 bug 钉死在测试里。

## 托盘图标：右下角"隐藏的图标"里那一个

Godot **没有**系统托盘 API，所以这个图标由辅助进程托管（和全屏检测**共用同一个进程**，
不多开一个）：

```
左键点图标 / 菜单「显示 / 隐藏」    收起或叫回她
菜单「退出桌宠」                   整个退掉（顺手把辅助进程收掉）
```

托盘和 Godot 之间靠一个小文件传命令（`user://pet_shell_cmd.txt`）—— 方向是反的：
状态文件是我们传给它的"结果"，命令文件是它传给我们的"动作"，读完立刻删。

三个实测踩出来的坑：

- **`Window.hide()` 对主窗口无效**：直接报 `Can't change visibility of main window`，
  而且是在 `_process` 里抛（真机表现就是"点了没反应 + 日志一堆错"）。改用
  `window_set_mode(MINIMIZED)` —— 她本来就不在任务栏里，最小化就等于消失。
- **最小化/还原会把"不进任务栏"那一位冲掉**：Windows 会重做一遍窗口样式，实测还原后
  `TOOLWINDOW=False`（她又冒回任务栏和 Alt+Tab 了）。所以还原之后必须重新设一次。
- **残留的命令文件会误伤下次启动**：上一次被强杀、或托盘点了退出没来得及删，命令就留在
  文件里，新一次启动会把它当成本次的命令执行 —— 实测一条残留的 `quit` 让新进程**刚起来
  就自己退了，而且什么都不打印**，极难查。现在启动时会先清掉它。

图标就是 `icon.png`（和窗口图标同一张）：导出版里 `res://` 不是真实路径，所以运行时先把它
读出来写到 `user://` 再交给辅助进程。脚本里那三个菜单文字是**中文但以 base64 存在** ——
`.ps1` 必须保持纯 ASCII（PowerShell 5.1 按 ANSI 读没有 BOM 的 `.ps1`，字符串里的中文会
直接变成语法错误、整个脚本一启动就死）。

> 验证：`tools/probe_tray.gd` —— 辅助进程有没有带托盘参数、图标文件对不对、命令通道
> （toggle 能收起/叫回、quit 能退）、以及还原之后各属性有没有丢。
> 图标"长什么样"没法从代码里断言，那部分得自己看一眼。

## 全屏时安静下来 + 更少的移动

三件事都是"别打扰你"：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `move_chance` | 0.35 | 待机时间到了之后**真的起身**的概率；没中就接着等一轮 |
| `idle_before_move` | (5, 13) | 待机多久才**考虑**动一次（秒，乘 `behavior_pace`）。原来 (2.5, 7) 且必定起身 |
| `quiet_when_fullscreen` | 开 | 检测到全屏就进"安静模式"；**关掉则不再留那个后台检测进程** |
| `quiet_radius` | 110 | 安静模式下允许离她当时位置多远（像素） |
| `quiet_idle_scale` | 2.5 | 安静模式下待机时间的倍率 |
| `quiet_move_scale` | 0.5 | 安静模式下单次移动时长的倍率；安静模式**不跑** |

实测（`tools/probe_quiet.gd` 跑 400 次"待机时间到"）：真的起身 **24.0%**，理论值
`0.35 × (1 − 0.3) = 24.5%` —— 改之前是**必定起身（100%）**，现在明显安静了。

> 顺序是先掷"做不做表情"（`emote_chance`，原地做手势、不算移动），再掷 `move_chance`。

### 安静模式的活动中心是"她当时所在的位置"，不是"家"

`home_anchor` 是家，但**不能**拿它当安静模式的活动中心：你一开全屏，她会被瞬间夹到
家的位置，看着就是**瞬移**。所以进入安静模式那一刻把当前窗口位置记成中心
（`_quiet_center`），之后才有"一小块"可言 —— 实测进入瞬间位移 0px。

活动范围还要和屏幕可用区域求交：家贴着屏幕右边时，光有半径会算出一个屏幕外的框。

### 全屏检测：一个常驻的 PowerShell 小进程

Godot 没有"现在有全屏窗口吗"这种 API，只能问系统。做法是在 `pet_shell.gd` 里内嵌一段
PowerShell、运行时写到 `user://`，用 `OS.create_process` 常驻跑一个 800ms 的循环，把
结果（`1`／`0`）写进 `user://pet_shell_state.txt`，Godot 这边读那个文件。

**为什么常驻而不是"隔几秒查一次"**：每次拉起 PowerShell 都有几百毫秒启动开销，几秒一次
等于一直在烧 CPU；常驻一个进程反而几乎为 0（循环体全是 P/Invoke，没有 cmdlet）。它每
~10 秒写一次心跳，所以 Godot 那边**文件超过 15 秒没更新就当作"检测死了"**，不会把过期的
"全屏中"当真（否则宠物会一直缩在小范围里不出来）。死了会自动重拉（冷却 20 秒、最多 3 次）。
退出时 `OS.kill` 收掉；脚本自己也会在发现宠物窗口没了之后退出 —— 实测退出后无残留进程。

### 判据是"所有顶层窗口"，不是"前台窗口"

第一版只看 `GetForegroundWindow()`，**实测是间歇性的**：一个窗口能不能真的拿到前台由系统
决定（后台进程调 `SetForegroundWindow` 经常被拒），所以真有全屏视频时也可能漏判。现在扫
所有顶层窗口，顺便也覆盖了"另一个显示器上全屏着"的情况。

两个必须有的过滤，都是在本机实测出来的：

| 过滤 | 为什么 |
| --- | --- |
| DWM cloaked | UWP／壳窗口的 `IsWindowVisible` 是 true，但其实是被遮蔽的（实测 `Windows.UI.Core.CoreWindow` cloaked=2） |
| `WS_EX_TOOLWINDOW` | 工具／离屏辅助窗口不是用户意义上的全屏应用（实测 IDE 的 `CEF-OSC-WIDGET`、桌面的 `Progman` 都是） |

少了这两条，答案几乎是**永久为"全屏中"**。

### 保持置顶：每 2 秒重申一次

别的置顶窗口（视频小窗、通知）会插到她前面，`pet_shell.tick()` 每 2 秒重申一次。

做法是**先关再开**：Godot 的 `window_set_flag` 在值没变时**直接 return**，连着设两次
true 根本不会去调 `SetWindowPos`。而且只在"当前本来就置顶"时才重申 —— 你要是从菜单里
关掉了窗口置顶，这里再强行打开就是跟你对着干。

> 验证用 **z 序编号比大小**（`tools/probe_quiet.gd` E 段）：置顶小窗出现后她=2／对方=1
> （被压住），几秒后她=1／对方=2（自己回来了）。用"她上面有没有东西"当判据**不行** ——
> 实测输入法（`IME`）窗口永远在最上层，那个问题永远返回"有"。

**盖不住的只有一种：独占全屏**（真去改显示器模式的那种全屏游戏）—— 那是 GPU 层面的模式
切换，任何用户态程序都盖不住。无边框全屏（现在绝大多数游戏和视频网站的全屏）能盖住。

### 但"每隔一会儿重申一次置顶"是错的：她会一闪一闪

原来是无条件地周期性调 `SetWindowPos(HWND_TOPMOST)`（先 2 秒一次，后来交给辅助进程
800ms 一次）。结果她**一闪一闪** —— 她的窗口是逐像素透明的，每次多余的窗口重排/重新合成
都看得见。实测 45 秒里就这么抬了 **51 次**。

现在只在**真的被盖住**时才抬：沿 z 序往上找，有真实窗口挡在前面才动。"真实"要过滤掉
Windows 自己那一堆永远在最上面的东西 —— 实测先被 `ThumbnailDeviceHelperWnd`（系统缩略图
辅助窗口）骗了一轮，又被 IDE 的 `CEF-OSC-WIDGET` 骗了一次。判据是：类名不在系统名单里、
**带 WS_EX_TOOLWINDOW 的不算**、**没有标题的不算**。现在稳定在 **60 秒 0 次**
（导出版 30 秒 0 次）。

> 另一个必须知道的 API 事实：`HWND_TOPMOST` 对**已经是置顶**的窗口**不会**改变它在置顶组
> 内的次序 —— 想把一个已经置顶的窗口抬到最前，要用 `HWND_TOP`。这是当初"让辅助进程去顶
> 菜单"那条思路失败的真正原因（它没报错，只是没动）。

## 开机自启动 & 隐藏任务栏图标（scripts/sys/pet_shell.gd）

菜单里「开机与系统」那一组的两条：

| 菜单项 | 默认 | 干什么 |
| --- | --- | --- |
| 开机自启动 | 关 | 登录 Windows 后自动启动桌宠（点了才写注册表，不替你做主） |
| 隐藏任务栏图标 | 开 | 不在任务栏和 Alt+Tab 里出现；桌面上照常显示、照常能点 |
| `自启动：已开启` | — | 纯显示的一行，读的是**注册表真实状态**，不是我们自己的开关 |

两个选择都存在 `user://pet_shell.cfg`；缺键时落回**检查器里的导出参数**（和聊天开关同一个套路，
不然新加的开关在老存档上会被读成 false）。

### 开机自启动：写 HKCU 的 Run 项，不碰 HKLM

用**用户级**注册表（不需要管理员权限，也不会影响别人）：

```
HKCU\Software\Microsoft\Windows\CurrentVersion\Run
  桌宠 = "<exe 路径>"                        ← 导出版
  桌宠 = "<godot.exe>" --path "<项目目录>"    ← 编辑器里（这样开发时也能先验证）
```

菜单那行状态是**去注册表读**的（只认 `reg query` 的返回码），不是读我们自己的开关 ——
用户可能在"启动项管理"之类的工具里把它关掉，那菜单就不该还打着勾。

两个坑，都是实测撞出来的：

- **写值不能走 `reg add`**：要写的那条命令里既有空格又有内嵌双引号，
  Godot 拼命令行时没法转义内层引号，`--path` 被拆成独立参数，reg.exe 直接报"无效语法"。
  现在改成叫 PowerShell 的 `Set-ItemProperty`，而且**名字和值都走 base64** —— 只剩 ASCII，
  中间过几层都不变形。
- **读回来也走 base64**：直接回文本时，中文路径读回来是 `妗屽疇`（UTF-8 字节被按 GBK 解）。
  注册表里存的**其实一直是对的**（外面用 `Get-ItemProperty` 逐字核过），但那种假乱码会
  把以后排查的人带沟里，所以干脆让辅助脚本只回 ASCII。

### 隐藏任务栏图标：Godot 那个 flag 在 Windows 上是空操作

本来以为 `DisplayServer.WINDOW_FLAG_POPUP_WM_HINT` 就够了，实测不行：

| 做法 | 结果 |
| --- | --- |
| `WINDOW_FLAG_POPUP_WM_HINT` | 窗口 ex-style **一位都没变**，始终带 `WS_EX_APPWINDOW`（= 强制给任务栏按钮） |
| `WINDOW_FLAG_POPUP` | 主窗口设它直接报 `Main window can't be popup` |
| 自己改 `WS_EX_TOOLWINDOW` | ✅ 有效：任务栏和 Alt+Tab 里都不出现 |

所以真活儿是叫 PowerShell 去设那一位（`WS_EX_TOOLWINDOW` 置上、`WS_EX_APPWINDOW` 清掉）。

**必须非阻塞调用**（`OS.create_process` 而不是 `OS.execute`）：改窗口样式会给我们
**自己的窗口**发消息（`SetWindowLong` / `ShowWindow`），主线程要是正卡在"等 PowerShell 返回"，
就成了互相等 —— 实测这么卡死过一次，180 秒超时，输出正好停在调用那一行。

脚本**内嵌在 `pet_shell.gd` 里**、运行时写到 `user://`，不是放 `tools/`：PowerShell 要的是一个
**真实文件路径**，而导出版里 `res://` 下不是资源的文件压根不进包。（脚本内容保持**纯 ASCII** ——
PowerShell 5.1 在没有 BOM 时按 ANSI 读 `.ps1`，里面写中文会变乱码。）

启动那次调用会让窗口闪一下（改完样式要让 shell 重新评估任务栏按钮，得 hide/show 一次），
大概 1 秒后生效。

### 但设一次不够：这一位会被反复冲掉

实测启动过程：**t=2s 设上、t=4s 就没了**，之后一直没回来 —— 因为 **Godot 自己一动窗口
（改尺寸、从最小化还原……）就会重算一遍窗口样式**，把这一位抹掉。所以现在是让辅助进程
**每 800ms 检查一遍并补上**（`Tick()` 里那段），不是"挑个好时机设一次"。

同一个原因还带来一个更隐蔽的问题：原来的"每 2 秒重申置顶"走的是 Godot 的 flag 机制，
**每重申一次就顺带把任务栏那一位冲掉一次** —— 表现就是任务栏图标忽隐忽现。现在置顶也
交给辅助进程用原生 `SetWindowPos` 做（带 `SWP_NOACTIVATE`，不会抢键盘焦点），两边不打架。

> 启动那 **~1.5 秒**仍然会有任务栏按钮：PowerShell 起来 + 编译 P/Invoke 要这么久。
> 之后就一直是隐藏的（导出实测 10/10 次采样都在隐藏状态）。

### 右键菜单被自己盖住

菜单（PopupMenu）是独立系统窗口（`embed_subwindows=false`）。它和宠物**都是置顶窗口**，
谁在上面取决于谁最后被抬起 —— 而宠物一移动（`window_set_position`）就会被 Windows 抬到
置顶组最前面，于是菜单一打开就被她盖住（实测 16 次采样，16 次输）。

改法：**菜单开着时把宠物从置顶里摘出去**（连 Godot 那边的标志一起摘，否则 Godot 会在
她下次动窗口时又加回来）。这样"菜单（置顶）在宠物（非置顶）之上"是 Windows 的硬保证，
跟先后顺序无关；菜单一关就恢复。实测 13 次采样 0 次被盖住。

> "菜单开着"这个信号是走意愿文件传给辅助进程的 —— 它当时先是被下面第 17 条那个参数坑
> 挡住，后来又被第 16 条那个转义坑挡住，所以光加菜单逻辑还不够，三处都要对。

> 验证：`tools/probe_shell.gd` —— 它**问 Windows 本身**要窗口 ex-style（而不是问 Godot），
> 再走一遍自启动的写→读→删。要带窗口跑，不能用 `--headless`。
> 导出版也实测过：exe 起来后窗口是 `TOOLWINDOW=True APPWINDOW=False`。

### 自启动没生效时，按这个顺序查

0. **先看 `%APPDATA%\Godot\app_userdata\桌宠\pet_start.log`**（每次启动追加一行：
   时间 / 可执行文件 / 命令行 / 自启动登记状态）。
   **没有这一次的时间 = 进程压根没被拉起来**，问题在系统那边，不在桌宠里；有就对比时间。
   > 这行**不能**指望引擎日志：导出版里 `print()` 不进 `logs\godot.log`（实测导出的
   > `pet.exe` 跑完，那个文件只有一行引擎横幅），而自启动跑的正是导出版 ——
   > 所以这行证据是自己写进 `pet_start.log` 的。
1. **确认是不是"真重启"**：`HiberbootEnabled = 1`（快速启动开着，Win10/11 默认）时，
   "关机再开机"是**从休眠恢复**，开机时间都不会刷新，也容易漏掉真正的登录流程 ——
   测试请用开始菜单里的**「重启」**，别用"关机再开机"。同理，**休眠/睡眠**不会触发自启动。
2. **看 Windows 有没有把它禁用**：设置 → 应用 → 启动。被禁用之后 Run 项还在，但不会执行，
   状态记在 `HKCU\…\Explorer\StartupApproved\Run`。
3. **手动跑一遍登记的那条命令**（`reg query "HKCU\…\Run" /v DesktopPet` 拿到值，粘进"运行"里）。
   能起来 → 登记没问题，回去看第 0/1/2 条。

### 这条命令为什么写得这么"笨"

登记的值就是**一条最普通的 exe 启动命令**（导出版 = exe 自己的路径；编辑器里 =
Godot + `--path`），路径用**反斜杠**、整条加引号。**不要**在这里加脚本、base64、
隐藏窗口之类的东西，两个坑都是实测撞出来的：

- **`.cmd` 里拼中文路径会散架**：cmd.exe 按 OEM 代码页读 `.cmd`，`…\桌宠` 落盘
  再读出来成了 `妗屽疇`，那条路径根本打不开（连 cmd 都会报"不是内部或外部命令"）。
- **`powershell -EncodedCommand` 那套被**杀软直接删了** ✗：隐藏窗口 + 编码命令 +
  拉起进程，正是恶意软件的典型特征 —— 报毒是应该的，自启动里不该出现这种东西。

**注意**：注册表里的值名也从「桌宠」改成了 `DesktopPet`（纯 ASCII）。原来那个中文值名
在这台机器上重启后**根本没被执行**，而且 Windows 的启动项记录里从来给它建过条目 ——
所以别再改回中文名。老的中文条目在关开关时会被顺手清掉。

**登记的是哪条命令**：导出版里点那个开关 → 登记 exe 自己的路径（自包含，不依赖别的）；
在编辑器里点 → 登记 `"<godot.exe>" --path "<项目目录>"`（这样没导出也能先验证）。
所以**开发时想让她跑最新代码，就在编辑器里开关一次；想要稳，就用导出的 `pet.exe` 开关一次**。
菜单那行状态会显示当前登记的命令是不是"当前这个位置"。

## 人格与长期记忆（pet_persona.gd / pet_memory.gd / pet_common_sense.gd）

### 她是谁：一行字是不够的

原来整份人设就是 `chat_system_prompt` 里的一行字（"你是住在主人电脑桌面上的蓝发女仆桌宠…"）。
问题不在"写得短"，而在**没给她边界** —— 模型只能自己填空，于是要么答得像客服，要么像个百科，
要么动不动"作为一个 AI 助手"。

现在人设分段写在 `scripts/ai/pet_persona.gd` 里，而且**拼装顺序是有意的**：
"她是谁"在最前面、参考资料在最后。放反了，模型会把参考资料当成任务书，语气立刻变成答题机器人。

| 段 | 写的是什么 | 为什么要有 |
| --- | --- | --- |
| 身份 | 18 岁、女生、今年 6 月刚高中毕业、暑假在家、住在电脑里 | 定死年龄和处境 |
| 不是 AI | 不许自称 AI/助手，不许说"我可以帮你" | 客服腔是最大的破功点 |
| 性格 | 小傲娇、迷糊、爱吐槽、明确的喜恶 | 给情绪反应一个有依据的来源 |
| 怎么说话 | 1~2 句、口语、不写 markdown、先接情绪再给方案 | 决定"像不像在发微信" |
| **认知水平** | 高中学的还记得；没上过大学、没工作过；**不会就说不会，禁止编造** | 最像真人的一块，也最容易被忽略 |
| 小习惯 | 顺口提自己刚在做的事；被问"你有身体吗"怎么带过去 | 让回复有"她刚才在干嘛"的连续性 |
| 关于主人 | 长期记忆（下一节） | |
| 现在 | 日期时间 + 她刚在做什么 | 所以她会知道"都十点多了" |
| 常识参考 | 按这句话的话题挑几条 | 见下 |

**认知边界那条是重点**：光说"你是 18 岁"没用，得写清楚*哪些会、哪些必须说不会*。
现在的效果（实测）：

```
主人：什么是傅里叶变换？
她：诶？加班加着加着突然问我数学…这个我没学过啦，只听说过名字，大学的东西吧。你讲给我听呗？

主人：3x+5=20，x 是多少？     她：x=5 呀。这个我还是会的，别小看多。
主人：你今年多大了？           她：十八呀，刚高考完，正在等录取呢。
```

### 常识：按话题挑，不整库塞

`scripts/ai/pet_common_sense.gd` 是一份"这个年纪该知道的事"（校园升学、学科基础、生活常识、
情绪人际、网络流行、社会常识、自然世界，约 60 条），外加按日期注入的时令条目。

不整库塞进 prompt 有两个原因：token 白烧；**更要紧的是会稀释人设** ——
参考资料越长，"她是谁"那几句的比重越低。所以按用户这句话里的关键词挑 5 条左右。

农历节日只写"有这么个节"、**不写具体日期** —— 日子每年都不一样，写死她就会报错日子，
那比不知道更糟。

### 长期记忆：把 giftia 那套机制移植过来

原来"记忆" = 内存里的 20 条对话历史：重启就没，聊长了也会被截断。
现在是把 `memory_manager.py`（那套确实做得不错）的**机制**移植成 GDScript：

| 机制 | 做法 |
| --- | --- |
| 遗忘曲线 | `R = e^(-t / (S*24+1))`，`S = 0.3 + 重要性*0.5 + min(复习次数*0.15, 1)` —— 被反复提起的记得牢 |
| 记忆分层 | 核心/重要/常规（按重要性 + 情感强度自动分配），遗忘强度 10/2/1，检索权重 1.0/0.8/0.5 |
| 重要性打分 | 情感强度 0.4 + 信息密度 0.3 + 被想起次数 0.2 + 长度 0.1 |
| 情感分析 | 12 类情绪的关键词表 + **语境翻转**（"我努力了还是失败了"不能判成开心）+ 程度副词/否定词 |
| 检索 | 两路召回（字面 n-gram 匹配 + 标签匹配）→ RRF 融合 → 按 检索质量.50 / 时间.20 / 情感.15 / 重要性.10 / 层级.05 重排 |
| 工作记忆 | 跨对话的整体摘要 + 还没聊完的话题 + 主人最近的情绪 |
| 档案卡 | 字段级事实（名字/年龄/职业/地点/生日/喜好/雷点/宠物/备注），**不受遗忘曲线影响** |

移植时降级的两处（环境里真没有，不是偷懒）：

- **语义向量 → 中文 n-gram 子串匹配**：giftia 用智谱 embedding，而桌宠直连 DeepSeek，
  它没有 embeddings 接口。好在 giftia 的 `_match_score` 本来就写了"向量不可用时降级到字符匹配"，
  移植的就是那一套。代价是**换个说法就可能找不着**（"我平时爱喝什么" vs 记忆里的"主人喜欢 冰美式"），
  所以补了一张 `TOPIC_HINTS` 话题扩展表。
- **SQLite / LangChain / mem0 → JSON 文件 + 桌宠自己的 chat 客户端**：不为记忆重新引入 Python 后端。

#### 提示词怎么排，才吃得到前缀缓存（2026-09）

服务商按"**逐字相同的最长前缀**"给缓存折扣，所以消息顺序是刻意设计的：

```
[system]    人设（她是谁 + 主人的额外要求）        ← 逐字不变，每次请求都一样
[user]      …历史…
[assistant] …
[system]    这一轮的上下文（关于主人 + 现在 + 常识）  ← 每轮都变
[user]      这一句
```

- 人设那半在 `PetPersona.build()`，**只放不会变的东西**；
  每轮会变的（记忆检索结果、日期时间、常识参考）在 `PetPersona.build_context()`，
  由 `PetChat` 的 `context_provider` 回调附到**历史之后**（见 `compose_messages()`）
- 这么排之前：记忆块夹在人设中间 → 缓存从那一句就断了，**连后面的历史都按原价算**。
  现在：稳定部分 1142 字 + 历史一路命中，一轮里只有末尾那条上下文（~150 字）不命中
- 上下文**不写进 `_history`**（它是"此刻的参考"，不是对话内容）——
  写进去的话下一轮的前缀就不再是这一轮的延长线了
- 实测确认：后端接受"历史中间插一条 system 消息"这种排法 ✓

> 验证：`tools/probe_memory.gd` 里有一组"缓存前缀"检查（人设两轮逐字相同 /
> 上下文单独一条且在历史之后 / 时间和记忆不在人设里）——
> `compose_messages()` 写成 static 就是为了能离线量这件事。

**实测（2026-09-22，官方 API + `deepseek-flash`，`tools/probe_cache.gd` 跑出来的）**：

| 那一发 | 提示共 | 命中 | 未命中 | 命中率 |
| --- | --- | --- | --- | --- |
| 人设单独一发 | 800 | 640 | 160 | 80.0% |
| 第 1 轮（人设+上下文+这句） | 885 | 640 | 245 | 72.3% |
| 第 2 轮（多一轮历史） | 934 | 768 | 166 | 82.2% |
| 第 3 轮（多两轮历史） | 972 | 768 | 204 | 79.0% |

三条从数据里读出来的机制（都反直觉，值得记）：

1. **命中按 64 token 一块跳**（640 = 10 块、768 = 12 块），不是按字算的
2. **服务商总会扣掉尾部约 160 token 不记命中**。旁证：把**完全一样**的请求原样发两遍，
   第二遍也只有 768 / 927。推测是写缓存有延迟 —— 所以"把人设字数凑到 64 的整数倍"
   收益很小（能拿回的顶多几十 token），**不值得为它改人设**。（这一条纠正了本文件
   早先"对齐 64 就能多拿一块"的说法）
3. **稳定命中的就是人设那一块**（640 = 10 块 ≈ 1118 字）。对话越长，命中率越被摊薄 ——
   所以唯一"白赚"的方向是把**每轮都在变**的那一段压小，而不是把稳定段堆长

**已经做的瘦身**（都是纯格式压缩，信息一条没少）：

- 人设里的"现在"**压成一行**（原来"现在是…"和"你刚才：…"分两行）
- 常识参考的标题压短（"下面这些是你本来就知道的事…"→"自然用上就行，别背原文"）
- **记忆块有 320 字上限**：超了就从**末尾**整行丢（末尾是按这句话检索出来的，丢了只是
  这轮少提一嘴；档案卡和工作记忆在前头，不丢），并且不留"只有标题、后面空掉"的段落

效果：每轮可变的那段从 161 字降到 127 字，第 1 轮命中率 70.9% → **72.3%**。

**应用自己也能量**（不用起探针）：

- `pet_chat.last_usage` / `last_once_usage`：原样存着服务商给的 token 账
- `cache_hit_tokens()` / `cache_miss_tokens()`：字段名各家不同（DeepSeek 给
  `prompt_cache_hit_tokens`、OpenAI 只给 `prompt_tokens_details.cached_tokens`），
  统一从这里取
- **调试版**每轮会打一行：`[桌宠] 这轮的 token 账：命中缓存 640 / 未命中 245（命中率 72%）`
  —— 正式版不打（导出后也没有控制台可看）
- 流式那条路要拿到 usage，请求里得带 `"stream_options": {"include_usage": true}`。
  官方 API 接受（实测流式那条路：第 1 句命中 640、第 2 句 768 ✓）；
  万一某个后端因此报 400，把 `pet_chat.send()` 里那一行去掉即可 —— 只影响"能不能看到账"，
  不影响聊天

#### 换后端要过哪几道：实测记录（2026-09-22）

**现在接的是 DeepSeek**：文本 `deepseek-flash`、看图 `deepseek-v4-flash-vision-exp`，
base `https://api.deepseek.com`（客户端自己接上 `/chat/completions`）。
key 只存在 `user://pet_chat.cfg` 里 —— **不进仓库**。导出版 `pet.exe` 和编辑器用的是
同一个 user 目录（`%APPDATA%\Godot\app_userdata\桌宠`），所以配置只改一处。

DeepSeek 这边实测（同一句"说一句十个字以内的话"）：

| `deepseek-flash` 默认 | 1.5 秒 | 708 字 | 正常 |

（"怎么应对"那列就是代码现在的行为）：

**"反应很慢"的根因：思考**（2026-09-22 实测）。GLM 这几个 flash 模型**默认都带思考**，
同一句"说一句十个字以内的话"：

| | 用时 | 思考 | 正文 |
| --- | --- | --- | --- |
| `glm-4.7-flash` 默认 | **15.3 秒**（峰值 42.6 秒）| 515~622 字 | **0 字**（预算被思考吃光）|
| `glm-4.7-flash` + `thinking:{type:disabled}` | **1.1 秒** | 0 字 | 正常 |
| `glm-5.3-flash` 默认 | 8.6~10.8 秒 | 830~1035 字 | 0~9 字 |
| `glm-5.3-flashx` 默认 | 3.1~3.3 秒 | 885~935 字 | 0 字 |
| `glm-4.6v-flash`（看图）+ 关思考 | 6.6 秒 | 0 字 | 正常 |

所以 `PetChat.no_think` **默认 true**，请求里带 `"thinking": {"type": "disabled"}`
（流式和一次性两条路都带）。桌宠要的是"像在发微信"的一两句话，
思考换不来质量，只换来十几秒的沉默。

不认这个参数的后端会回 **400** → `_note_unsupported()` 自动把它摘掉并记住，
之后不再发（**换模型不会因为这一项卡死**）。`glm-5.3-flashx` 就不认这个参数，
它本来也快（3 秒），会自动走到"不带 thinking"那条路。

真机三条路各跑过一遍：**流式**主动开口（含 `%%` 候选）✓ / **后台 `ask_once`**（记忆抽取，
实际写进 1 条）✓ / **看图**（发红橙色图，它答"橙"）✓。跑的过程中真的撞上两次 429，
**都被自动重试救了回来** ✓。

> 自己测：`godot --headless --path . --script res://tools/probe_cache.gd`
> （它自己发请求，第一发量人设、后三发量对话）。
> 换个后端跑同一条命令，如果**没有** `prompt_cache_*` 字段，说明那个后端不做前缀缓存，
> 那么"提示词怎么排"对省钱就没有影响。

**实时时间 / 距上次说话**（让她"在过日子"）：

- `PetPersona.now_line()`：读系统时钟，精确到分钟（`2026年9月22日 周二 19:51，晚上`），
  时段用口语（说"晚上"不说"20 时"），凌晨会补一句"主人这么晚还没睡"的情境提示
  （**只写情境、不写成台词**，不然她每句都提这件事）。每次发消息都会重算，所以是实时的
- **距上次说话多久**：宿主在 `_context_for()` 里算好传进来（`gap_min`），
  3 分钟会说"距上次说话 3 分钟"、300 分钟说"5 小时"。**不给就不提** ——
  免得她编"我们好久没聊了"。这条让她分得清"刚聊过"和"隔了大半天"

记忆是怎么长起来的（两条路）：

1. **本地规则**（零成本、立刻生效）：抽自述式的话（"我叫…""我不喜欢…""记住…"）写进档案卡。
2. **模型抽取**（`memory_ai_extract` 开着时）：每轮对话后发一次非流式请求
   （`PetChat.ask_once`，**单开一条连接，不打断正在流的对话**）。提示词照搬 giftia 那版的严格规则：
   只取"明确说出"的、禁止推测、禁止把 AI 的建议当成用户的事实。取回的存成记忆条目。
   另外每 `memory_summary_every` 轮更新一次工作记忆。

> 抽错的记忆会留在档案里、反复影响后面所有对话，所以宁少勿滥：
> 规则抓不到的先不管，模型那边用"只输出 JSON + 没东西就返回 `[]`"兜着。

### 主动说话 / 偷看屏幕说的内容，也会进记忆（但要"选择性"）

打字聊天是**整轮**记下来的（历史 + 工作记忆 + 抽事实）。主动搭话、偷看屏幕、
看摄像头这三条**不能**这么干 —— 它们每天会产生好几条，而且大多是
"嗯嗯～""嘿嘿"这种，整轮存进去会把档案冲成流水账，把真正重要的事挤掉。

所以它们走的是**四道筛子**（在 `_note_observation()` 里，逐层收紧）：

| 筛子 | 挡掉什么 |
| --- | --- |
| 1. 长度 / 中文实字数（`PetMemory.worth_remembering`） | "嗯嗯～""嘿嘿"这种没信息量的，**连模型调用都不用发** |
| 2. 文本去重（`pet_memory.add()` 里比对） | 同一句说过就不再记一遍 |
| 3. 重要度 + 遗忘曲线 | 信息量低的自己淡掉、被清掉 —— 这是最后一道，也是"选择性"真正落地的地方 |
| 4. AI 二次筛选（`memory_ai_extract` 开着时） | 让模型只挑"**关于主人**的事实"（她在做什么、在意什么），挑不出来返回 `[]`。撒娇、感慨、玩笑在这一层被挡掉 |

第 4 道用的是 `PetMemory.OBSERVE_PROMPT`（和从主人话里抽事实的 `FACT_PROMPT` 分开）——
因为它面对的是"她自己说的话"，要提炼的其实是**她在屏幕/摄像头里看到了什么**，
比如她说"你在忙活呀，挺赶的样子"，值得记的是"主人当时在赶一个活儿"。

记下来的形式带来源前缀，她以后才能顺着提：

```
她偷看屏幕时看到：主人在赶一个活儿，好像挺赶的
她主动聊到：……            （她自己找的话题）
她看摄像头时看到：……
```

后台那条抽取请求和聊天共用同一个节流（`memory_ai_every_sec`）——
不能因为她多看了几眼屏幕就多花钱。整个开关是 `memory_observe`。

### 她主动说话时给"快速回答"，一直不理她会生闷气

**快速回答**：她说完话，**气泡下面会冒出几个按钮**，点一下就当你说过那句话（25 秒后自动收起）。
两个时机：她主动开口之后（概率 0.7）、以及**聊天之后**（概率 **0.20**）。

**为什么是概率而不是每次都给**：每次都给就成了一张"必看的表"；有时有、有时没有，
才像随手递过来的一句话。两个概率都能在设置面板里调（`quick_chance` / `quick_chance_chat`）。

**按钮上的字分两层**：

1. **本地那组立刻顶上**（`quick_options_for`）—— 要"立刻"能点，等模型一秒多就不叫快速回答了。
   顺序每次打乱，而且尽量不跟上次同一个开头（池子就那几句，原样重复一眼能看出是写死的）
2. **模型那组随后换上去**（`quick_ai`）：拿她刚说的那句再问一次小模型，让它现编三句更像样的。
   洗不干净 / 没回来 / 关掉开关，就继续用本地那组 —— **按钮不会因为模型乱答而消失**
3. **她自己先开口时，候选和那句话一起给出来**（宿主 `_send_first`）：提示词末尾让她说完之后
   另起一行写 `%% [候选…]`，宿主用 `split_options()` 切开 —— 前半句进气泡，候选直接交给
   快速回答模块，**省掉原来那次"再问一次模型编候选"的请求**（少一次往返、按钮也不迟到了）。

   用 `%%` 而不用 JSON 是刻意的：她的话里随时可能出现引号（中文引号、书名号、"啊？"），
   一出现就把 JSON 弄坏 —— 而"她的话"是最不该被格式绑住的东西。
   `%%` 之前那半句照旧**边生成边冒字**（`_on_chat_token` 会把最后两个字符先憋住，
   免得 `%` 漏进气泡）；模型没照格式写 → 候选为空 → 自动退回第 1、2 层那套做法

| 坑 | 说明 |
| --- | --- |
| 后台那条连接被记忆占着 | 记忆抽取 + 摘要每轮能占十几秒，**挤在一条连接上就永远轮不到** —— 所以候选在 `pet_quick.gd` 里单开一个客户端 |
| **客户端没人 tick** | 拆模块时漏了 `_client.tick()` —— 请求发出去没人收结果，表现成"AI 那组从来不出现"、`is_busy()` 永远 true。**客户端的状态机得由持有它的模块每帧推**（见 `pet_quick.gd` 的 `tick()`）|
| 模型偶尔只吐思考、正文是空的 | 它的思考走 `reasoning_content`，**预算被思考吃光**正文就是空（实测 120/300 都空、1200 起才稳）。所以给 2000，并且**空返回时同一轮再试一次** |
| 气泡 1.8 秒就淡出 | 按钮会跟着一起消失，而模型那组要几秒才回来 —— 显示按钮时把气泡**按住**（`hold_with`），按钮收起时再让它淡出 |
| `Dictionary` 是引用类型 | `var want := _quick_want` 之后再 `_quick_want.clear()`，会把 `want` 自己也清空 —— 必须 `duplicate()`（踩过，报的是"键不存在"） |
| 异步回来的东西要认领 | 模型那条几秒后才回来，这期间她可能又说了别的 —— 用"第几代"（`_quick_gen`）认领，过期就丢掉 |

### 2026-09 修过的两个"选项不对"

1. **本地那组答非所问**：她问"吃饭了没呀？"，按钮给的是"在呢，你说""刚在忙，怎么啦？" ——
   那组本来是给"她主动搭话问你忙不忙"用的。本地那组**不可能知道她问了什么**，
   所以现在 `chat` 里的问句只给三句"打太极、任何问句都接得住"的话（"嗯…让我想想"），
   真正接得上的答案交给模型那条
2. **AI 那组永远看不到**：三个原因叠在一起 ——
   ① 客户端漏了 tick（见上表最后一行）；
   ② 提示词里**没有上下文**，模型只能瞎猜她刚才说了什么，编出来的话接不上 ——
	  现在把最近几轮对话一起发过去（`_quick_context()`，并把她刚说的那句去掉，免得重复）；
   ③ 按钮 25 秒就收，而模型要 8~10 秒才回来 —— 现在**有请求在路上时会多挂一会儿**（`AI_GRACE_MS`）

现在的实测（官方 API + `deepseek-flash`）：本地那组 1.5 秒顶上 → AI 那组 8~10 秒换上去，
而且她问什么就答什么：

```
她：你洗完快去躺，别又抱着手机刷到十二点。
按钮：["行，我洗完就躺。", "不刷了，你困先睡。", "等我会儿，马上就来。"]
```

嫌 AI 那组慢（快慢全看后端）就在设置面板里把「按钮用哪个模型」指到一个不思考的快模型，
留空 = 跟聊天同一个。

- **按钮得能点到**：桌宠平时只把"角色轮廓"设为可点区域，其余一律穿透到后面的窗口，
  所以按钮显示时 `pet_pointer.gd` 会把按钮的矩形**并进可点区域** ——
  不做这一步，按钮飘在轮廓外，点上去直接穿过去，就成了个摆设
- 点了之后走的是正常发送链路，所以这句话也会进记忆
- 菜单里那几条（摸头 / 喂食 / 让她想个话题）也都能把按钮带出来

**生闷气**：她主动说完话后 **90 秒**没人理 → 委屈度 +1，并说一句出来
（AI 能用就用她自己的口气说，不能用就退本地台词 `LINES_SULK`）。

- 委屈**不靠硬编台词**，而是写进人设的【现在】（`_sulk` → `pet_persona.gd`），
  所以接下来几轮她的口气会自然带出来，也不会每句都翻这件事
- **被理了就消气**：聊天、摸头都算（`_soothe()`）
- 连续被冷落（委屈度 ≥ 2）才**选择性**记进记忆，而且半小时内不重复记 ——
  走的是和偷看屏幕**同一条观察通道**（四道筛子照过）。记下来长这样：

```
她生闷气时说：……
（场景说明里带"主人很久没理她"，所以模型能提炼出"主人很久没理她"这件事）
```

### 摸哪儿反应不一样（头 / 胸 / 手 / 腿）

点她身上不同地方，反应是不同的 —— 部位在 `pet_pointer.gd` 的 `classify_touch()` 里判：
把**按下时**鼠标的位置换算成"在角色外接矩形里的比例"，再按分带归类。

| 部位 | 分带（归一化坐标） | 反应 |
| --- | --- | --- |
| 头 | 上 26% | 亲昵（原来那组摸头台词）+ **消气** |
| 手 | 两侧（离中线 26% 以外）且在上 2/3 | 害羞 / 牵手那种 + 消气 |
| 胸 | 中间 26%~52% | **明确不乐意**：凶他、**不消气**，委屈度 +0.5 |
| 腿 | 下 28% | 怕痒 / 躲 + 消气 |
| 身体 | 其余（腰腹那一段） | 随口应一句 + 消气 |

几个刻意的设计：

- **摸到胸必须明确不乐意**。一个 18 岁的女孩子不会笑嘻嘻地接受——写软了这个人物立刻就假了。
  而且 **20 秒内第二次就"屡教不改"**：话变硬（`LINES_STOP`）、委屈度 +1，还会
  `memory.add()` 记一笔"主人手欠" —— 以后她自己会防着点
- 摸到不该摸的**不消气**，反而加委屈度；这条情绪线和"被冷落"是**同一条**（`_sulk`），
  写进人设的【现在】，所以之后几轮她的口气会自然带出来
- 为什么要"按下时"的位置：`_end_drag()` 那一刻鼠标已经松开了，位置不准；
  而且拖拽结束和"点一下"共用这个回调，拖完手一定挪过地方
- 判部位靠**分带**而不是网格：这个模型是 722 个节点的刚体层级（没有 skin），
  按网格判非常费劲；分带还更好调，想改手感就改那几个数字
- 菜单里的「摸摸头」没有坐标（`_press_pos` 是 INF），所以默认按 **head** 算 —— 菜单项本来就叫摸头

### 摸太频繁：她会主动开口，并把这事记下来

一分钟内摸到 8 下（**摸胸算两下**，所以摸胸 4 次就到线），她就不只是冒一句话了 ——
而是**主动开口让你停手**，并把这事写进长期记忆。

为什么要走"她自己开口"那条路（`_last_origin = "touch"`）而不是直接 `_say()` 一句：
那样只是在气泡里闪一句、看完就没了。走这条路她会**真的开一次口**：

| 顺带得到的 | 说明 |
| --- | --- |
| 快速回答按钮 | 单独一组（"好啦不摸了"、"手放好了，别生气"）。**不能给她"摸摸头，等会儿陪你"** —— 那是又摸她一下 |
| 计入"主人多久不理我" | 你还不理她就接着生闷气（`_sulk_watch_ms`），和前面那套是连着的 |
| 进长期记忆 | 见下 |
| 委屈度 +1 | 写进人设【现在】，之后几轮口气自己带出来 |

记忆那一笔**用本地规则先落下**（`memory.add()`），不依赖 AI、也不花一次请求 ——
这句话写死在 `_touch_complain()` 里。半小时内不重复记（和生闷气共用 `SULK_STORE_GAP_MS`），
否则一晚上能存十条同义句。origin 是 `touch` 的回复**不再走** `_note_observation()` ——
那会变成同一件事存两条，所以 `_note_observation()` 里对 `touch` 直接返回。

后端没起来 / 正忙时退本地台词（`LINES_TOUCH_STOP`），但"开始等她回话"这一步照做 ——
和生闷气一个待遇。

> 验证：`tools/probe_memory.gd` 的离线段里有 6 条分带检查 + 5 条"摸太频繁"的检查
> （7 下不喊停 / 第 8 下喊停 / 摸胸算两下 / 4 次摸胸到线 / 一分钟前的旧记录会过期）。
> `touch_burst_hit()` 写成 static 就是为了能脱离场景验证 ——
> 窗口和相机那一套在无头模式里跑不起来。

### 长时间不理她：先偷看一眼屏幕，然后她自己看着办

被冷落 90 秒后的**第一次**，她不是直接闹，而是**偷看一眼屏幕**（复用「偷看屏幕」那条链路），
看一眼你在干什么。但**看到之后怎么理解、要不要闹、闹到什么程度，全交给她自己** ——
提示词只交代"你在偷看"和她的处境，不给任何判断规则：

```
（主人好久没理你了。你自己偷看了一眼屏幕，看看他到底在忙什么。看到什么就照实说一句，
然后按你自己的想法决定要不要闹、闹到什么程度 —— 想懂事一点也行，想小小地闹一下也行，
一两句话，别长篇大论）
```

实测（真截图 + 真模型，2.8 秒）：

> 哦……你在搞那个什么Godot？还一堆报错，看着就头大，难怪不理我。
> 哼，忙你的吧，我不吵你，等你搞完记得理我一下就行。

她自己在"懂事"和"闹"之间找了个位置，两头都沾一点 —— 这正是不该由我们硬编的地方。

**否定过一版做法（留个记录，别再走回去）**：让她开头输出 `[忙]` / `[闲]` 标记，
本地把标记摘掉，再按它把委屈度压到 0.5（原谅）或抬到 1.5（继续闹）。两个毛病：

1. 她看到的是**自由文本**（在赶活儿 / 在打游戏 / 在写代码），本来就落在"忙"和"闲"之间，
   硬压成两个值必然丢信息；
2. 判断的后果是我们硬写的，可能和她自己说的话对不上 —— 嘴上"你去忙吧"，
   下一句还在闹别扭，读起来就是两个人格。而且为了"别让标记闪进气泡"，
   流式那条还得攒住开头几个字（`_on_chat_token` 里那段），纯属自找的复杂度。

现在看到什么、怎么想、说什么是一条线下来的。代价说清楚：**"他在忙 → 委屈度自动降到 0.5"
这个行为没有了** —— 委屈度按"被冷落了几轮"继续累着（你哪次真回她，`_soothe()` 一次性清零），
她当时怎么判断的则**进长期记忆**（「她看屏幕时看到：…」）。也就是说这件事由她记着、
下次聊起来自然带出来，而不是我们替她记一个数。

第一次之后要是还不理她，就不会再看第二眼，直接继续闹 —— 看一次是"在意"，
一直看就成盯梢了。

> 偷看看到的东西本身有信息量（你当时在忙什么），所以这条**比单纯闹脾气更容易进记忆**：
> 闹脾气要连着被冷落两次才记，偷看这条只要过了半小时的间隔就记 —— 记成「她看屏幕时看到：…」。

**存储**：`user://pet_memory.json`（档案卡 + 工作记忆 + 记忆条目三块）。

> 验证：`tools/probe_memory.gd` —— A 段离线验机制（抽取/否定守卫/遗忘/分层/检索/存盘读回），
> B 段用你配的服务真跑 7 轮对话、**并把整份人设提示词打出来**，C 段验 AI 抽取。
> 它用临时记忆文件，跑完就删，不动你的真记忆。

**`PopupMenu` 不是 `Control`**（它是 `Popup → Window`），`add_theme_font_override`

```gdscript
var th := Theme.new()

menu.theme = th
```

> 写这段时踩了一次：参数类型写成 `PopupMenu`，再拿 `Button / Label / LineEdit` 去调，
> 直接**整脚本编译失败**（`Invalid argument for _apply_font(): argument 1 should be …`）。
> 面板上的控件走 `Control`，菜单走 Theme，两条路不能混。

### 「退出」点不动（已修）

症状：右键菜单里点「退出」**毫无反应**，其它条目都正常。

原因不在退出那一步，而在**根菜单从来没连过 `id_pressed`**：子菜单是在 `_submenu()` 里
各自连的，而根菜单上的条目（「退出」，后来还有「设置…」）走的是根菜单自己那条信号，
谁都没接。于是点击被 Godot 正常发出、正常高亮、然后**掉在地上**。

```gdscript
# 子菜单各自连，根菜单也得连 —— 漏了这一句，菜单看起来一切正常，只是点了没反应
if not _menu.id_pressed.is_connected(_on_item):
	_menu.id_pressed.connect(_on_item)
```

这类 bug 读代码很难发现（信号、条目、id 全都对），所以固化成了探针：
`tools/probe_settings.gd` 第 1 段就断言"根菜单的 `id_pressed` 至少接了一个回调"。

退出还顺手做干净了三件事（`_quit()`）：收起面板（输入框正抢着键盘焦点时看着像没反应）、
主动收掉托盘辅助进程（不等它自己发现我们没了，图标立刻消失）、存一次设置。

### 表驱动：加一项设置只动三处

面板长什么样、值怎么钳制，全部来自 `pet_settings.gd` 里那张 `SECTIONS` 表
（`k` 键名 / `t` 控件类型 / `label` / `hint` 鼠标提示 / `min·max·step` / `options·vals`）。
主脚本那边只多一张 `SETTING_VARS`（键 → 检查器变量名）。所以加一项设置要动的地方是：

1. `pet_settings.gd` 的 `SECTIONS` —— 长什么样、范围多少；
2. `desktop_pet.gd` 的 `SETTING_VARS` —— 存到哪个变量（按钮和系统那几个例外，见 `_apply_settings`）；
3. `SETTING_SAVED` —— 要不要落盘（漏了就是"能改能保存，重启又变回去"，界面上完全看不出来）。

第 3 条是最容易漏的，所以有个交叉检查：`tools/probe_memory.gd` 的离线段会遍历表里每个键，
断言"主脚本认它 **且** 它会落盘"。

### 几个刻意的设计

- **提示一律做成鼠标悬停**（tooltip），不占一行版面：25 项每项都带一行灰字说明的话，
  滚一屏都看不完
- **危险动作不做弹窗确认**：项目里 `embed_subwindows=false`，弹窗会变成**另一个 OS 窗口**，
  而桌宠平时是 `no_focus` 的，那种窗口很难收场。改成"同一个按钮点两下"（5 秒内）
- **面板占满整窗**，不是居中固定尺寸：窗口本身只有 330×470，缩放档还会把它变小，
  固定尺寸在小档下会溢出到窗外
- **输入框的字色必须自己指定**：我们把底色换成了白的，但默认主题的字色是给深色底准备的
  浅灰 —— 结果是"打进去的字几乎看不见，只有光标在动"。勾选框同理
  （这个毛病原来的 AI 设置面板里就有，只是没人细看）

### 值存在哪、什么时候生效

- **检查器变量**（`@export`）是出厂值，也是运行时的唯一出处；
  `user://pet_chat.cfg` 记你改过的那些（`chat` 段是老的四个开关，`app` 段是面板新加的）
- 打开面板时主脚本把**运行时真实值**灌进去（自启动去注册表读、隐藏任务栏读 shell），
  不是读存档 —— 两边不一致时以真实状态为准
- 点保存后：落到变量 → 落盘 → **立刻生效**（重数那几个倒计时、重拼人设、按新设置调 shell）

> **这里踩过一个真坑**：`_apply_settings()` 多了一个 `push_system` 参数，启动时传 `false`。
> 原因是启动时读回来的只是"上次的偏好"，而自启动的真实状态在注册表里，可能在
> 任务管理器里被关掉过 —— 每次启动都按我们记的值写一遍注册表，等于把别处的改动盖掉。
> 具体后果是：`autostart_enabled` 这个导出变量默认 `false`，存档里是 `true`，
> 于是流程变成"启动 → 比对不一致 → `set_autostart(false)`"，**一开机就把用户开着的自启动关了**，
> 而且完全看不出来是谁关的。只有用户在面板里点保存才该写注册表。

## 离线假死：联系不上时她只做基础动作（hibernate_when_offline）

判据只有一个（`_offline()`）：聊天总开关关着，**或者**后端探活失败。
开局那一两秒探活还没回来，她也先按离线算 —— 保守方向是对的，宁可安静，别往死服务上撞。

进了假死，**停掉的全是会自己发起的事**：

| 停 | 为什么 |
| --- | --- |
| 主动说话 / 生闷气 | 本来也会退本地台词，但那样她等于一直在"假装聊天" |
| 定时偷看屏幕 / 看摄像头 | 截了图也没地方发，连截图这步都省（摄像头也别对着空气开） |
| 记忆抽取 / 工作记忆摘要 | 那些请求注定失败，白花时间 |
| 聊天发消息 | 挡下来并说清楚"联系不上"，**输入框里的话不动**，连上了你重试就行 |
| 聊天那条派活（"干活：…"） | 同上。**工作台那条不受限** —— 那是你明确的指令，dsh 有自己的账号，让它自己报成败 |
| 自己乱走 | 待在原地（这道门在骰子**前面**，`move_chance` 调到 1.0 也压不住它） |

保留的（基础功能）：摸头 / 喂食 / 睡觉 / 拖拽 / 菜单 / 本地台词 / 眨眼呼吸 ——
被摸了照样有反应，只是不再主动做事。

怎么知道她进了假死：

- 菜单「聊天与 AI」最底下那行状态（`AI 服务：已连接 / 联系不上（她先只做基础动作）/ 聊天总开关关着`）
- 断网那一刻她说一句（**只说一次**，不每轮探活失败都念叨），恢复时再说一句"好了"

开关：检查器里的 `hibernate_when_offline`（默认开）。关掉 = 断网时她照旧装作没事
（探活照样 15 秒一次，聊天发送照样会失败，只是她不"躺平"）。

> 验证：`tools/probe_offline.gd` —— 直接拿 `PetChat.reachable_set()` 把探活结果扳成离线
> （那就是结果落地的那条路），逐项断言"该停的停了、该留的留着、恢复后又能走"。
> 注意测试要在几秒内跑完：真探活 15 秒一次，后端若是通的会自动把状态翻回去。

## 让她调用本机 DeepSeek Harness 干活（scripts/sys/pet_harness.gd）

右键 →「聊天与 AI」→ 打开「让她用 dsh 干活」，然后在聊天框里说：

```
干活：用一句话说明为什么天空是蓝色的
```

她先按住气泡说一句，跑完把结论**用自己的口气**讲回来：

```
我：干活：用一句话说明为什么天空是蓝色的
dsh：天空之所以是蓝色的，是因为阳光中的蓝光波长较短，被大气中的气体分子强烈散射（瑞利散射）……
她：因为蓝光波长最短，被空气里的小分子散射得到处都是，所以抬头一看就是蓝的啦～
```

dsh 的原文另外留一份在聊天记录里（她只会转述一两句，长的东西得能回头看）。
派活的说法认好几种：`干活：` `干活:` `dsh：` `dsh:` `/dsh ` `让dsh `。

### dsh 是什么、为什么这么调

`@deepseek-ai/dsh` 是装在本机 npm 缓存里的 agent harness，平时双击 `DeepSeekHarnessLauncher`
会用 `node bin.js web` 起个 Web UI（127.0.0.1:3080）。我们用的不是那个界面，而是它的
**一次性任务模式**：

```sh
dsh --profile headless "任务文本"     # 跑一个全新会话，答案打到 stdout，退出
```

官方原话是"不开端口、不留后台，适合脚本、CI 与一次性任务"，退出码 0 = 完成。实测一句话的小任务 4~6 秒。

不去 HTTP 调它那个 Web 服务，三个理由：一次性模式本来就是给脚本用的（stdout 即答案、退出码即成败，
比猜它家前端的接口稳得多）；不管 3080 在不在跑都能用；不用管它的登录态和会话列表。

### 推理档按工作量自动配

dsh 的 deepseek 适配器只认四档 `off / low / high / max`（`off` = 不开思考），而 headless
**没有对应命令行参数** —— 这一项属于"设置层"，真源是 `~/.dsh/settings.yaml` 里的
`agent-default-model.reasoningEffort`（官方 README 特意注明它"刻意不是配置字段"）。所以流程是：

```
估一档 → 临时改设置文件 → 跑 → 原样改回去
```

估分（`effort_score()`）是几个维度相加，权重写死成常量，好照着自己调：

| 维度 | 权重 |
| --- | --- |
| 长度 | 40 字 1 分，最多 2.5（再长不代表更难） |
| 拆成几件事（换行 / "然后""另外"） | 每个 +0.7，最多 2.1 |
| 重活关键词（分析 / 设计 / 为什么 / 代码…） | 每个 +1.2，最多 4.8 |
| 轻活关键词（"一句话""翻译""查一下"…） | 每个 -0.8，最多 -2.4 |

分数 → `off`（<1）/ `low`（<2.5）/ `high`（<5）/ `max`。另外两条兜底：

- **带了重活关键词的至少给 `low`** —— 否则"用一句话说明为什么天空是蓝色的"会被"一句话"
  扣成 `off`，可它问的是"为什么"，不想一下就答只能背课文
- 设置里的「最高推理档」是**天花板**：想让额度有上限就压低它，任务再大也不会超过

> 实测：`现在几点` → off（4.5 秒）｜`为什么天空是蓝的` → low｜
> `分析一下这段代码为什么报错` → high｜`设计一个登录方案，然后写测试，另外评估性能` → max

### 两个不得不绕的坑

**1）中文乱码 → 多一个 node 转发器**

直接用 `OS.execute` 收 dsh 的 stdout，中文回来是 `1 鍔?1 绛変簬 2銆?` —— Godot 在 Windows 上
按系统 ANSI 代码页解码子进程输出，而 node 写的是 UTF-8；错的不只是显示，有些字节直接变成 `?`，
**不可逆**。（任务**传过去**是好的：Godot 拼命令行走 CreateProcessW，中文没问题，坏的只有回收输出这一段。）

所以让 node 帮个忙：运行时写一个十几行的转发器到 `user://pet_harness_runner.js`，
它用**文件描述符**把 dsh 的 stdout / stderr 接到两个文件上（原始字节，一个字节都不动），
我们再按 UTF-8 读回来。顺带白拿 stderr = 它那串推理流。

**2）不能卡住她 → 工作线程**

`OS.execute` 要等子进程结束（一次五秒起），在主线程里调就是把桌宠卡住。所以丢给一个工作线程，
主脚本每帧 `poll()`。线程里只写几个字段（bool / String / int），不碰场景树、不发信号，跑完 join。

### 会动别人的文件，所以特别小心

`~/.dsh/settings.yaml` 是你的文件，我们只做一件事：把那一行的值换掉，跑完**把读到的整份内容
原样写回**（不引 YAML 库、不重排任何一行 —— "顺手整理一下配置文件"正是这类功能最典型的翻车方式）。
改档那两步是纯字符串函数（`with_effort()`），探针拿几份样例直接比输入输出：

- 键在 → 换值（保留它自己的缩进），**不增删任何行**
- 键不在但段在 → 补在段里（缩进照抄同段），不能掉到文件末尾变成顶级键
- 连段都没有 → 末尾整段补上

读不到设置文件就不改它（宁可这一趟用你原来的档）；退出时也会还原。

### 开关与其它

- **默认关**：它会在你机器上真跑一个 node 进程、花你的额度，这种事得你主动开
- 开关在两处：右键 →「聊天与 AI」→「让她用 dsh 干活」，以及设置面板的「AI 服务」那一组
- 跑活期间她会按住气泡，`_ai_busy()` 也算上它 —— 这时候跟她说话，她会说"我还在弄那件活呢"
- 退出时不掐正在跑的活（dsh 是一次性进程，跑完自己退），但设置文件一定还原
- 找不到 dsh 时她会直说找不到（而不是没反应）；`bin.js` 是**扫**出来的，不写死 npx 那个哈希目录
  （官方启动器写死了，换版本就失效）

> 验证：`tools/probe_harness.gd` —— A 段离线（估档 / 封顶 / 派活前缀 / 改设置文件的三种情况），
> B 段真跑一个任务并**确认设置文件被原样改回去**。用法：`-- --offline` 只跑 A 段。

## 工作台：让她给自己升级（scripts/ui/pet_workbench.gd）

右键 →「工作台…」（一级菜单里）。这个面板是**给"正儿八经的活"**用的，
尤其是**让她改自己的代码**：

```
工作台 / 档位 high｜权限 read-only
在哪儿干    [D:\项目\桌宠] [项目目录]
			☑ 自我升级（附上项目说明，并允许改文件）    ← 勾了就把工作目录指到项目、并允许改文件
			☐ 允许她改文件
要她做什么  [给小蓝加一个"今天几号"的菜单项            ]
			[派活] [清空]                     推理档按任务自动挑
结果        [（dsh 的原文都在这儿，不经过她的转述）    ]
			[打开工作目录] [重启她（应用改动）] [关闭]
```

| | 聊天框里的「干活：…」 | 工作台 |
| --- | --- | --- |
| 适合 | 顺手的小活（查一下、算一下） | 正儿八经的活、**改自己的代码** |
| 结果 | 她**用自己的口气转述**一两句（人设不破） | **原文摆在这儿**（她要转述就丢了细节） |
| 任务长度 | 一行 | 好几行 |
| 工作目录 / 权限 | 继承默认（只读） | 能选，还能"允许改文件" |
| 干完 | 她说完就完 | 能一键**重启她**加载新代码 |

### 自我升级这一圈是怎么转的

1. 勾「自我升级」→ 工作目录指到项目目录、自动勾上"允许改文件"、任务前面加一段项目说明
   （她是通读代码的人，那段只说"这是哪儿、从哪看起、改完要跑什么验证"）
2. 派活 → dsh 在**你指定的工作目录里**读代码、改代码
3. 结果原文留在这儿；想看她动了什么就点「打开工作目录」
4. 点「重启她（应用改动）」→ GDScript 是启动时加载的，不重启不生效

权限那一步在 dsh 那边只放宽到 **`workspace-write`** —— 也就是**只能改工作目录里的东西**，
改不到别处去。`danger-full-access`（不限制范围）**故意不提供**：自我升级用不着，
那等于把整台机器交出去。

两个刻意的细节：

- **不勾"允许改文件"时不会去动你原来的权限设置** —— 只看代码、回答问题用不着改它。
  这一项的做法是"需要放宽时才临时放宽"，绝不主动写回 `read-only`（你本来配的可能是别的档）
- 跑完**原样写回**（和推理档同一套，见上文那个纯字符串函数）：`k` 个键都在同一个
  `settings.yaml` 里，一次改完一次写回 ✓

工作目录这么猜（猜错不致命，面板里能改，改完记住）：`res://` 下有 `project.godot` 就用它
（编辑器里跑、从源码跑）；否则看 **exe 旁边**哪个子目录里有 `project.godot`
（导出版用 junction 指回源码的情况，实测 `dist/pet.exe` 旁边就是 `pet/`）；
都没有就用 exe 所在目录。

「重启她」的顺序是**先拉起新进程、再退自己** —— 反过来的话会有一小段"旧的没了、新的还没起来"。
怎么拉起自己沿用开机自启动那套规则（导出版 = exe 自己；编辑器里 = Godot + `--path`），
所以不管她从哪跑起来的，重启后还是原来那个形态。

> 实测（真给它写权限、工作目录指到项目里）：让它新建一个文件，6.9 秒做完，文件真写出来了，
> 内容也对；跑完 `settings.yaml` **原样还原**（`high` / `read-only` 一位没变）。

> 版面这个坑值得记一句：状态那行字一开始和"标题 + 弹簧"挤在同一行，
> 而它带自动换行 —— 结果被压到只剩几像素宽，**竖着排成一条**，高度撑到一百多像素，
> 把下面所有东西顶出窗口。截图才发现（`hint()` 那种带 autowrap 的标签别和弹簧同行）。

## 整合启动：一个 bat 把 AI 服务和桌宠一起拉起来

`启动桌宠.bat` 做两件事：**先确认 deepseek-web-api 在跑**（不在就 `node start.mjs` 拉起来，
最多等 24 秒），**再启动桌宠**。服务没起来也不影响桌宠运行，只是聊天退回本地台词。

### 写 bat 的三个坑（`启动桌宠.bat` 之前一直是坏的）

早期版本**根本启动不了桌宠**，症状还很难懂：cmd 报 `'t-Null' 不是内部或外部命令`
—— 一行命令被拆成碎片逐个执行。三个原因叠在一起：

| 坑 | 表现 | 正确做法 |
| --- | --- | --- |
| bat 行里的 `\|` | cmd 当管道符，PowerShell 一行命令被劈成两半，后半段当命令执行 | 一行里别用 `\|`，改用 `> $null` 重定向 |
| UTF-8 + 中文 + LF 换行 | cmd 按当前代码页逐行解析，多字节字符和 LF 会让解析错位 | bat 保持**纯 ASCII + CRLF** |
| `--path "%~dp0"` | `%~dp0` 结尾是反斜杠，`\"` 被当成转义引号，整条命令行拆坏（实测 0 个进程；改成 `"%~dp0."` 立刻正常） | 结尾补一个点：`"%~dp0."` |

最后一条最隐蔽：**原版就是这个写法，也就是说它一直是坏的**，只是平时多半从编辑器 F5
启动才没暴露。两个 bat 都已按上表改好（非 ASCII 字节 = 0、全 CRLF），实测
`启动桌宠.bat` 能正常拉起 `桌宠 (DEBUG)` 窗口。

## 模型与动画优化

原文件 `peekdeek.gltf` **10.8 MB**（722 节点、567 个方块网格、151 个动画），
优化后的 `peekdeek_opt.glb` **1.30 MB**，**小了 7.9 倍**。

原始文件和它的 import 都**原样保留**，没有覆盖。

### 数据是怎么省下来的

分析结果（用 `tools/analyze_gltf.mjs` 量的）：6.83 MB 的二进制数据里有 **6.07 MB 是动画**，
而且两个动画严重注水：

| 动画 | 关键帧 | 时长 | 问题 |
| --- | --- | --- | --- |
| `MainAnim` | 282,882 | **4,312 秒** | 实际只是 4 条轨道在轻微呼吸摆动，导出时被拉成了 72 分钟 |
| `hold_mainhand$minecraft:mace` | 32,235 | **1,000 秒** | 同上，桌宠完全用不到 |

另外整个 buffer 是以 **base64 内嵌**在 JSON 里的（912 万字符），光编码开销就很可观。

优化做了四件事：

1. **glTF → GLB**：二进制 buffer 不再 base64，直接省掉三分之一
2. **砍掉用不到的动画**：151 → 33，桌面宠物真正需要的只有这些
3. **`MainAnim` 限时重采样**：4,312 秒 / 28 万帧 → **24 秒 @ 8Hz**，只留 772 帧，
   呼吸摆动的手感保留下来，体积从 5.13 MB 降到几 KB
4. **删掉恒定不变的轨道**：共 550 条，这些轨道不携带任何信息
   （Godot 导入时也会做，但先删掉能少让编辑器啃一堆数据）

**没有动的东西**：节点层级、节点名、网格、材质、UV、贴图。所以所有保留下来的动画
依然驱动着完全相同的节点。

### 保留下来的 33 个动画

- **基础**：`idle` `walk` `walkBack` `run` `jump` `sneak` `sit` `sleep` `climb` `swim` `fly` `death` `attacked`
- **互动**：`use_mainhand` `use_offhand` `swing_hand` `swing_offhand` `BlinkEye` `BlinkTwo`
- **表情动作**：`extra0` `extra2`~`extra7`
- **其他**：`MainAnim`（已重采样）、`ladder_up/down/stillness`

`idle` 和 `MainAnim` 在运行时被合并成一个 `__pet_idle`：`MainAnim` 是 24 秒的呼吸摆动，
压到 `idle` 的 3 秒周期上，两条循环就对齐了，互不冲突的轨道才会被合并
（见 `scripts/desktop_pet.gd` 的 `_build_idle_anim()`）。

眨眼动画被放进**第二个 AnimationPlayer**（运行时创建），且拷入时用 `_strip_to_face()`
裁到只剩 `/Face/` 下的轨道 —— 因为原始 `BlinkEye`/`BlinkTwo` 其实覆盖全身（39 条轨道），
不裁的话走路中眨眼会把全身钉成站立姿势（见下文「走着走着突然变成静止姿势在滑行」）。

### 动画的两个坑

**1. 持续动作必须手动开循环。** 导出的 glb 里动画 `loop_mode` 默认是 `LOOP_NONE`，
播完就停在最后一帧 —— 走路/跑步"走到一半突然定住"就是这么来的。
`_apply_loop_modes()` 启动时把 `LOOPING_ANIMS` 里那些持续动作统一设成
`LOOP_LINEAR`（实测打开 14 个）。顺带也修掉了 `sit` / `sleep`：它俩长度只有
0.001 秒，之前播完会立刻触发 `animation_finished` 被弹回待机。

**2. 一次性动作的等待时间要按动画自身长度算，不能写死。** 实测：

| 动画 | 长度 | 旧写死值 | 结果 |
| --- | --- | --- | --- |
| jump / swing_hand / attacked / use_mainhand | 0.375 ~ 0.75s | 0.6 ~ 1.2s | 够 |
| extra0 ~ extra6 | 1.0 ~ 1.5s | 1.6s | 够 |
| **extra7** | **7.5s** | 1.6s | **播到 1.6 秒就被切走** |

所以改成 `_play_action()`：等待时间 = `动画长度 / anim_speed + 缓冲`。

### 修掉的两处模型/交互毛病

**1. 左腿骨骼下混着右腿的方块**（"有一只脚的部分方块跟着另一只脚走"）

用 `tools` 里的分析脚本把小腿三层骨骼下的方块坐标全列了一遍，发现左脚骨骼
（`LeftFoot13`）下挂着一块 `local_x = +0.119` 的方块 —— 模型中线在 x=0，左腿在负侧，
所以这块其实长在**右腿**那边，却跟着左腿摆动。

而右脚骨骼下已经有一块位置**完全相同**的方块（`RightFoot7`，同为 0.119），
所以它是个重复件。`desktop_pet.gd` 的 `_fix_crossed_leg_parts()` 在 `_ready()` 里
按位置做了一次校正：另一侧已有同位置方块就移除，否则挪过去并保持世界变换 ——
两种情况都不改变静止姿势，只修正"跟随哪条腿"。

顺带一提，排查时有个坑：**Godot 导入 glb 会给重名节点加数字后缀**，
骨骼实际叫 `LeftLeg9` / `LeftFoot13` / `RightFoot11`，用精确名字是找不到的，
只能用前缀匹配 + "该节点直接挂着 MeshInstance3D"来识别骨骼（方块节点也叫
`LeftFoot4` 这类名字，但它们是叶子）。

**2. 鼠标碰到角色时窗口会闪一下**

原来的做法是在"整窗可点"和"整窗穿透"之间切换，靠 `window_set_mouse_passthrough()`
来回设区域。这个 API 的参数是**接受鼠标事件的区域**，每次调用都会让 Windows
重建窗口区域，闪的那一下就是这么来的。

现在改成把可点区域**固定成角色所在的矩形**（外扩 `catch_padding`），只在包围盒
真的变化（>1.5px）时才更新；鼠标进出角色完全不动窗口，空白处照样穿透。

## 后期渲染 / 抗锯齿收敛（白边问题）

原来的配置会在轮廓上出现一圈偏白的描边。查下来是**三个设置叠在一起**造成的，
其中最主要的一个是贴图导入参数：

### 根因

把贴图拆出来量了一下：256×256，**完全不透明 31.4%、完全透明 68.6%、半透明 0%**
——是一张硬边像素画，alpha 只有 0 和 1 两种值。

但是那圈"完全透明、又紧贴着图案"的 texel，RGB **并不是黑色**：

| | 透明环平均亮度 | 其中偏亮的比例 |
| --- | --- | --- |
| 修复前 | **0.638** | **49.8%** |
| 修复后 | **0.000** | **0%** |

也就是说，轮廓外面那一圈 texel 里存着大量接近白色的 RGB。原来的贴图导入设置是：

```
compress/mode=2            # VRAM 压缩 S3TC/BPTC
mipmaps/generate=true      # 生成 mipmap
process/fix_alpha_border=true   # 把边缘颜色扩散进透明区
```

`fix_alpha_border` 会把图案边缘的颜色向透明区扩散，配上 VRAM 压缩和 mipmap 的
多次降采样，那圈透明 texel 就被填成了亮色。而方块模型用的是**线性过滤**，
每个方块的边缘都会采到这一圈 —— 于是整圈轮廓被掺进了白色，看起来就是"抗锯齿白边"。

### 改了什么

**贴图导入**（`peekdeek_opt_0.png.import`）：

| 参数 | 原来 | 现在 | 原因 |
| --- | --- | --- | --- |
| `compress/mode` | 2（VRAM/S3TC） | **0（无损）** | 贴图才 30 KB，压缩省不了空间，反而在色块边界产生伪影 |
| `mipmaps/generate` | true | **false** | 像素画用不上 mipmap，降采样只会把透明区颜色混进边缘 |
| `process/fix_alpha_border` | true | **false** | 就是它把亮色填进透明环的 |

**采样方式**：材质的 `texture_filter` 设成 `TEXTURE_FILTER_NEAREST`。
方块模型的每一个面都是轴对齐的矩形，UV 正好落在 texel 边界上，最近邻采样最准、
也彻底不会串色（这也是 Minecraft 类画风的通行做法）。
代码里在 `desktop_pet.gd` 的 `_harden_materials()` 统一设置，566 个 surface 共用 1 个材质。

> 顺带记一下：**Godot 4 的 PNG 导入面板里没有"采样过滤（Filter）"这一项**。
> 导入面板能控的只有 mipmap、压缩方式、fix alpha border、normal map 这些；
> 采样过滤只存在于**材质**的 `texture_filter` 和项目默认的
> `rendering/textures/default_filters/`（那里也只有各向异性等级和
> use_nearest_mipmap_filter，没有 3D 的 Filter 选项）。
> 所以"把 Filter 改成 Nearest"这件事，在这个项目里是在代码里做的。

**抗锯齿**：

这个模型是"方块 + 像素画贴图"，锯齿其实有两个来源，得分开治：

| 锯齿来源 | 用什么治 | 说明 |
| --- | --- | --- |
| 几何边缘（方块轮廓、斜角） | MSAA | 只跟三角形边界有关，贴图设置帮不上忙 |
| 贴图镂空边缘 | alpha scissor | alpha **混合**的边缘 MSAA 是无效的，改成 scissor 才吃抗锯齿 |

对应设置：

| 设置 | 原来 | 现在 | 原因 |
| --- | --- | --- | --- |
| `anti_aliasing/quality/msaa_3d` | 2（4x） | **3（8x）** | 轮廓锯齿交给 MSAA，它只作用在几何边缘 |
| `anti_aliasing/quality/screen_space_aa` | 1（FXAA） | **0** | 它在透明背景下只磨 RGB 不磨 alpha，会把轮廓掺黑 —— 见下文「透明背景下别用 SMAA / FXAA」 |
| `scaling_3d/scale` | 1.0 | **2.0（2 倍超采样）** | 用来压方块之间的亚像素缝隙，见下 |
| `environment/defaults/default_clear_color` | 默认 | 保持默认 | 实测改它对这个透明窗口没有任何影响 |

**超采样（`scaling_3d/scale = 2.0`）**：内部按 660×940 渲染，再降采样回 330×470。
整数倍超采样对像素画本身是安全的（方块面 UV 落在 texel 边界上，2×2 降采样不跨边界），
它主要用来减轻**方块之间那些亚像素缝隙**造成的白线（成因见下面的 TAA 一节）。

代价是过渡像素变多、而且平均亮度偏高：

| | 轮廓上的过渡像素 | 这些过渡像素的平均亮度 |
| --- | --- | --- |
| `scale = 1.0`（8x MSAA） | 659 | 0.555 |
| `scale = 2.0`（8x MSAA + 2x SSAA） | 807 | 0.624 |

也就是轮廓外会多出一层很淡的过渡带。两害相权，白线比这层过渡带扎眼得多，
所以留着开着；不想要的话把 `scaling_3d/scale` 改回 `1.0` 就行。

**材质**：`_harden_materials()` 除了设置采样和 alpha 抗锯齿，还会把
`TRANSPARENCY_ALPHA` 统一换成 `TRANSPARENCY_ALPHA_SCISSOR`（阈值 0.5）。
贴图 alpha 是二值的，scissor 的裁切结果和 alpha 混合完全一样，
但边缘能被 MSAA 抗锯齿，而且不需要深度排序、方块之间不会互相串色。

**TAA 与透明窗口互斥**：

上面那圈白线的成因是**方块之间的亚像素缝隙**：相邻方块面之间有道小于 1 像素的缝，
背景从缝里透出来，而 MSAA 的采样点盖不住它。TAA 靠跨帧抖动 + 累积正好能填掉 ——
放大对比图里，头发、深蓝袖子、裙摆边缘的白线在开 TAA 之后基本消失。但它有个硬条件：

| 渲染器 | TAA | 透明像素 |
| --- | --- | --- |
| mobile | 开 | 118552 —— 但 **TAA 被引擎拒绝**：<br>`TAA is only available when using the Forward+ renderer.` |
| forward_plus | 关 | 118487 |
| forward_plus | 开 | **0** ← 整个画面变成不透明 |

所以 **TAA 和"只有人物"的透明窗口没法同时要**，只能二选一。
默认选了透明那一侧：`use_taa = false`、`opaque_background = false`。

真要用 TAA：`use_taa = true` + `opaque_background = true`，
渲染器 `renderer/rendering_method` 改成 `forward_plus`（TAA 只在 Forward+ 下可用）。
此时背景变成 `background_color` 铺的浅色卡片（实测 `(0.97,0.97,0.98)`
经 filmic tonemap 后渲染成 `(0.957,0.957,0.961)`）。

### 透明背景下别用 SMAA / FXAA（实测会做出深色描边）

`screen_space_aa_mode` 有 关闭 / FXAA / SMAA 三档，SMAA 原理上是单帧后处理、
不要求不透明背景，看起来正好适合"透明 + 抗锯齿"——但它实测是**帮倒忙**的。

做法：同一机位、同一姿势在透明背景下渲染三张图，再逐通道 diff。

| 对比 | alpha 有变化的像素 | RGB 有变化的像素 | 轮廓像素平均亮度 |
| --- | --- | --- | --- |
| 关闭 vs FXAA | **0** | 9242 | 0.609 → 0.537 |
| 关闭 vs SMAA | **0** | 7430 | 0.609 → **0.454**（单点最大差 0.58） |

两件事一目了然：

- **alpha 一个像素都没动。** 屏幕空间抗锯齿只做边缘检测后混合 RGB，不碰 alpha，
  而轮廓的锯齿恰恰长在 alpha 上 —— 该磨的地方一点没磨到。
  三张图的半透明像素数完全相同（都是 1267 个），轮廓形状一个像素没变。
- **被磨暗的只有 RGB。** 轮廓外侧透明区的 RGB 是纯黑（见上文「图集边缘外扩」的实测），
  SMAA 把黑混进边缘像素，合成到桌面上就是一圈**深色描边** ——
  正好是原来那个"白色轮廓"的镜像毛病。

所以默认是**关闭**。透明窗口里唯一真正管用的抗锯齿是 **MSAA 8x + 2x 超采样**：
它们在**采样阶段**生效，会真正磨到 alpha，轮廓才会真的变平滑。

### 方块棱边上的"白色小锯齿"（两个叠加的原因）

鞋子边缘放大 10 倍，每条棱边上都挂着一串**点状白珠子**。用逐项关掉的对照实验量了
该区域亮度 > 0.5 的像素数（`tools/zoom_crop.gd` 的变体参数）：

| 配置 | 亮(>0.5)像素数 |
| --- | --- |
| 初始 | 20 |
| 关掉镜面高光 | 4 |
| 关掉镜面高光 **+ UV 内缩半 texel** | **0** |
| 关掉光照 | 0 |

两个原因叠在一起，得分别处理。

#### 原因一：UV 越界采样（真正让棱边采到亮 texel 的那个）

先排除"是不是方块之间的缝透出了背景"：把同一张透明渲染图分别合成到**深色底**和
**白底**上，那些亮点的颜色**完全不变** —— 说明它们是不透明像素，不是背景。

再查它们采的是贴图哪个 texel（`tools/uv_probe.gd` 打印每个面 UV 矩形内外各 2 个 texel）：

```
RightFoot8 右边: -1(92,45)a=0.00 rgb=0.57,0.60,0.76  →  +0(93,45)a=1.00 rgb=0.95,0.91,0.95  ← 白袜子
RightFoot7 左边: -1(74,61)a=1.00 rgb=0.10,0.13,0.31  →  +1(72,61)a=1.00 rgb=0.95,0.84,0.90  ← 亮色
RightFoot6 上边:  ±0(72,30)a=1.00 rgb=0.15,0.15,0.15 →  +1(72,29)a=1.00 rgb=0.91,0.82,0.82  ← 浅色条纹
```

**这张 256×256 的图集里，不同部件是紧挨着排的**：鞋面（深色 `rgb≈0.11`）的 UV 矩形
右边 1 个 texel 就是白袜子，上方 2 个 texel 就是浅色条纹。而面片的 UV 正好压在 texel
边界上，**MSAA 的着色又是按像素中心求值的** —— 边缘像素的像素中心可能落在三角形之外，
插值出来的 UV 就越过矩形边界，一越界采到的就是隔壁的亮 texel。

这也解释了它为什么对 TAA / SMAA / FXAA / MSAA / 超采样全都无感：那些都作用在
**覆盖率或时间累积**上，而这个问题出在 **UV 采样位置**上。

**修法**：`_inset_uvs()` 把每个面的 UV 朝自己的 UV 包围盒中心收缩半个 texel
（`uv_inset_texels`，默认 0.5），边缘像素就永远停在本面最外那一排 texel 之内。
纹理内容几乎不变（只有最外一小条 texel 的映射被压掉）。

> 实现细节：一个方块面拆成的两个三角形各自都含该矩形的 3 个角，所以两者的 UV 包围盒
> **完全相同**，共享的那条对角边会算出同样的结果 —— 不会在面中间撕出一条缝。

#### 原因二：镜面高光把这些亮 texel 又"点亮"了一遍

导入后的材质是 `specular_mode = Schlick-GGX` + `metallic_specular = 0.5`（实测），
Fresnel 在**掠射角**趋近 1；而方块模型的每条棱边恰好都是掠射角，于是整圈棱边都被
反射的环境光加亮。修 UV 之前那些亮点的颜色是 `rgb≈(0.85,0.85,0.94)`，
正好等于环境光色 `(0.86,0.9,1)`。

**修法**：`_harden_materials()` 里 `specular_mode = SPECULAR_DISABLED`
（`disable_specular` 开关，默认开）。像素画本来就是无高光的平面着色。

> 两个开关都能在检查器里关掉做对比：`disable_specular` 立即生效，
> `uv_inset_texels` 是启动时生效的，改了要重启。

### "extra 做一半就回到静止动画"：动画自带一段静止尾巴

现象：宠物播 `extra` 时，动作做到一半就像回到静止姿势了。

先排除"状态机把它切走了"这个方向。`tools/probe_watch.gd` 让宠物以高频动作模式
跑了 130 秒（只缩短等待时间，计时机制一个字没改），**77 次切换里
"上一个动画没播完就被切走" 0 次** —— 状态机是干净的。另外单独验过
"打断一个动作会不会补发 `finished` 信号"（`tools/probe_interrupt.gd`）：不会。

真正的原因在动画数据里。`tools/probe_pose_curve.gd` 用"两帧之间动得最厉害的那个
节点位移了多少"（取最大值，不用平均 —— 一个挥手只有几个节点在动，平均会被大量
静止节点稀释成 0）量出每个动作**真正做到哪一刻**：

| 动画 | 长度 | 动作实际做到 |
| --- | --- | --- |
| extra0 / extra4 | 1.50s | 70% |
| extra5 | 1.00s | 72% |
| extra2 / extra3 | 1.50s | 82% / 85% |
| extra6 | 1.25s | 100% |
| extra7 | 7.50s | 100% |

也就是说这些 extra **做完手势就回到站立姿势空转**，后面那段其实没在动。
而计时按动画全长算，宠物就会在那儿杵着等 —— 看着正是"做一半又回到静止动画"。

**修法**：启动时逐个量出动作结束时刻（`_measure_action_ends()`），一次性动作的计时
用它而不是全长（`action_tail_trim`，默认开）。实测 `extra0` 的动作计时
**2.49s → 1.85s**（它的手势 1.5s 就做完了），动作演完就接下一个，不再空等。

判据细节：单步位移要同时超过**绝对下限**（1.5 厘米）和**本动作峰值的 15%**。
只用一个都不行 —— 只用绝对下限时，静止尾巴上那点回正残留会被当成"还在动"，
结果只裁到 83%（等于没修）；只用峰值比例时，遇到本来就很轻的动作会把整段判成没动。

> 改完之后的状态机行为：动作计时到期会主动切到下一个动作，此时**切点在静止尾巴里**
> （`extra0` 在 1.84s 处切走，而它的手势 1.5s 就结束了），这是有意为之。
> 想恢复"按全长等完"就把 `action_tail_trim` 关掉。

### "行走时不播走路/跑步动画"：一个状态卡死 bug + 走跑分离

先说结论：**移动路径本身没有问题** —— `tools/probe_watch.gd` 让宠物只走路/跑步跑
90 秒（`-- 90 0` 把 `emote_chance` 设成 0），16 次移动**每一次都真正调用了动画**
（0 次被 `_play` 跳过），31 次切换 0 次被切走。

真凶在**点击路径**上：走路中点一下角色（几乎不动鼠标），`_begin_drag()` 会把
`_state` 设成 `DRAG` 并播 `jump`；松开时 `_end_drag()` → `_react_click()`，
如果正好落在**摸头冷却**（`pet_cooldown`）里，旧代码直接 `return`，
**没人把 `_state` 从 `DRAG` 拉回来**。后果是连锁的：

- `_begin_move()` 只在 `IDLE` 状态触发 → 从此**永远不再走路/跑步/做表情**；
- `_on_main_finished()` 又被 `DRAG` 守护挡住 → 动画换不回去，
  宠物**僵在 `jump` 的最后一帧**。

外观正是"该走的时候不播走路动画"。修法：冷却分支里把状态拉回 `IDLE`。
`tools/probe_drag_state.gd` 复现并验证了修复 —— 修复前第二次点击后 `_state` 永远
卡在 `DRAG`，修复后 3 秒内宠物恢复自己走路（`state=WALK`，动画=`walk`）。

**走跑分离**：原来走路和跑步共用一个 `move_duration`，现在拆开：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `walk_duration` | (2.0, 6.0) | 一次走路持续多久（秒） |
| `run_duration` | (1.0, 2.5) | 一次跑步持续多久；跑步费劲，默认更短促 |
| `run_chance` | 0.22 | 一次移动是跑步的概率（原有，不变） |

### "走着走着突然变成静止姿势在滑行"：两层自愈兜底

这个症状是"窗口在平移（WALK 状态）、动画却是静止的"。给状态机加了**两层自愈**，
不管根因是哪条路径，症状都会在一帧内被纠正：

1. **`_ensure_walk_anim()`**：每帧在 WALK 分支里检查"动画必须是 walk/run"，
   不对就立刻纠正（debug 构建会打印一条 `走路中动画跑偏` 便于追查是谁改的）。
2. **`_on_main_finished()` 的循环修复**：正常情况下 walk/run 是循环动画、永远不会
   `finished`；走路中收到 `finished` 就说明循环丢了 —— 补回 `LOOP_LINEAR` 并重新播放，
   否则动画会僵在最后一帧而窗口继续平移。

写自愈时踩了一个值得记的坑：第一版把它放在 `_step_move()` **之后**，而
`_step_move` 结尾可能调 `_start_idle()` 把状态改成 IDLE、动画改成 `__pet_idle` ——
自愈拿着过期的 WALK 假设又把动画改回 walk，两者打架（探针实测待机只活了 0.04 秒）。
所以自愈必须在 `_step_move` **之前**，并且守护里显式确认 `_state == State.WALK`。

> 顺带说明：100 秒真实配比（`emote_chance=0.3`）的自动观察里，状态机本身没有产生过
> "WALK + 静止动画"（44 次切换全部一致）。所以如果还看到这个症状，最可疑的是
> **拖拽路径**：宠物走到光标下时点了一下角色 → 进入 DRAG 播 `jump`（0.5 秒后停在
> 末帧）→ 窗口跟随鼠标 = 平移。这两层自愈对 DRAG 不生效（那是刻意的拖拽行为）。

**真正的根因后来找到了：眨眼动画覆盖全身。**
两层自愈上线后症状仍在 —— 因为自愈盯着的是"主 player 在播什么"，而毛病出在
**第二个 AnimationPlayer（眨眼叠加层）** 上。实测 `BlinkEye` / `BlinkTwo` 各有
**39 条轨道，和 `walk` 的轨道集合一模一样**（Root、四肢、裙子全有），只是身体部分的
键值恰好是站立姿势。眨眼在任何状态下都会随机触发（平均 7 秒一次），叠加层在场景树里
排在主 player 后面、同节点冲突它赢 —— 于是走路途中一眨眼，全身被钉成站立姿势
0.7~1.1 秒，窗口却照常平移。这正是"突然变成静止动画并且平移"。

修法：`_scan_animations()` 把眨眼动画拷进叠加层时，`_strip_to_face()` 只保留
`/Face/` 下的轨道（眼皮 / 眉毛 / wink，实测裁到 14 条），身体继续由主 player 驱动。
注意必须 `duplicate()` 再裁，否则会把主库里共享的同一份动画资源也裁掉。
验证见 `tools/probe_blink_walk.gd`：修复后眨眼期间腿部活动帧 84/90（与基准一致），
修复前的完整版对照只有 47/90 且带一次 0.17 的猛 snap。

### 鼠标穿透会让窗口整体"提亮"

这个坑值得单独记一笔。`window_set_mouse_passthrough()` 在 Windows 上是靠
**`SetWindowRgn` 裁剪窗口区域**实现的，实测副作用是：**被裁出来的可见区域
整体会多一层很淡的提亮**，桌面图标看着发白，而且提亮的边界正好落在角色轮廓上
—— 很容易被误判成"背景被光照照亮了"（跟光照没有任何关系）。

同一块屏幕区域，运行中 vs 关闭后的平均像素差：

| | 角色轮廓内 | 轮廓外 |
| --- | --- | --- |
| 开穿透 | 明显提亮（+8 ~ +10 / 255） | 精确 0.00 |
| **关穿透** | **干净** | 精确 0.00 |

所以 `mouse_passthrough_enabled` 默认是 **false**：
"背景绝对干净" 和 "空白处能点到后面的窗口" 只能二选一。

### 导出版"发白发灰"的真相（之前那份结论是错的）

**旧结论（错）**：以为"导出的 exe 无法启用 Windows 窗口透明"。
**真实原因**：**背景色的 RGB 没被清零**，被 DWM 当成预乘 alpha 数据**加**在了桌面上。

透明 viewport 里，清屏色/背景色的 **alpha 会被置 0，但 RGB 会原样保留**。
于是窗口帧缓冲变成"alpha=0 而 RGB≠0"，而 DWM 是按预乘 alpha 合成的 ——
等价于把那点 RGB **加到**桌面上，表现就是整块均匀发白/发灰。

判定依据（同一像素，开/关宠物窗口对比，同时抓一块远离窗口的对照区）：

| | 有宠物 | 无宠物 | 差 |
| --- | --- | --- | --- |
| 修之前 | 183,183,199 | 30,30,46 | **+153**（≈ sRGB(0.3)，正是不透明的默认清屏色） |
| 修之后（导出） | 66,66,82 | 30,30,46 | **+36** |
| 修之后（`--path`） | 66,66,82 | 30,30,46 | **+36** |
| 对照区（远离窗口） | 24 | 24 | **0** |

两个要点：

- 差值**恒定、不随底色变化**。如果只是"半透明叠加"，差值会随底色变；
  恒定说明是**加法混合**，而不是"窗口没拿到透明"。
- 修完之后**导出版和 `--path` 完全一致**（都是 +36）。这个 +36 是两种模式都有的基线，
  不是导出版特有的，也就说明导出版的透明已经正常了。

**修法**：`project.godot` 里加一行

```
environment/defaults/default_clear_color=Color(0, 0, 0, 0)
```

透明模式下 `_apply_background()` 还会顺手把 `env.background_color` 也清成全透明，双保险。

> **最终结论（根因已定位）**：这是 **Vulkan 后端（Forward+ / Mobile）在透明窗口下写出的帧缓冲
> 没有做预乘 alpha** —— 背景的 RGB 原样保留、alpha 却是 0，而 DWM 按预乘 alpha 合成，
> 等价于把那点 RGB **加到**桌面上，于是出现那层白。
>
> **换成 Compatibility（OpenGL）渲染器后彻底消失**：同一个位置，开/关宠物窗口的像素差
> 从 `+36,36,36` 变成 **`0,0,0`**。
>
> ```ini
> renderer/rendering_method="gl_compatibility"
> ```
>
> 同一场景、固定姿势下两种后端的对照（`tools/shot_alpha.gd` + `tools/measure_alpha_edge.gd`）：
>
> | | Vulkan (Forward+ / Mobile) | OpenGL (Compatibility) |
> | --- | --- | --- |
> | 不透明 / 全透明 | 35486 / 118347 | 35496 / 118228 |
> | 轮廓半透明像素 | 820 个 | 817 个 |
> | **轮廓像素平均亮度** | **0.609**（未预乘，偏亮） | **0.261**（已预乘，正确） |
>
> 像素数量基本一致，说明 MSAA + alpha scissor 照常生效；亮度比约等于平均覆盖率，
> 正是"有没有预乘 alpha"的差别 —— 顺带也解释了轮廓上那圈偏亮的白边。
>
> 逐项试过、**都不是**原因：Forward+ / Mobile 之间切换、MSAA 开关、2x 超采样开关、
> `background_mode`（`BG_CANVAS` / `BG_CLEAR_COLOR`）、把清屏色压到 0.001、
> 以及 `xr/shaders/enabled`（那是 VR 用的，和这个无关，已移除）。

> 顺带删掉了之前那段"导出版强制切不透明卡片"的逻辑（`OS.has_feature("template")`）——
> 它是基于错误结论加的，留着反而会让导出版莫名其妙变成一张白卡片。

> **Camera3D 自己挂了 `environment` 时会覆盖 WorldEnvironment**，只改 `$WorldEnvironment`
> 是不生效的。`_apply_background()` 现在改的是**真正生效的那个**
> （`_effective_environment()`：相机上挂了就用相机的）。

### 导出成 exe（分发 / 独立运行）

流程就是 `项目 → 导出 → Windows Desktop`，预设和导出模板都已就绪，**不用改任何开关**。

透明形态在编辑器里和导出版里表现一致（见上一节），所以直接导出即可。
`opaque_background = true` 时才会走卡片形态，卡片底色由 `background_color` 控制。

#### 导出时的两个坑

1. **当前预设是 `binary_format/embed_pck=false`**，产物是 **`wi.exe` + `wi.pck` 两个文件**，
   分发时必须一起拷贝，只给 exe 是打不开的。想只发一个文件就在导出面板里勾上
   **Embed PCK**。
2. **测导出版之前先关掉编辑器的嵌入窗口模式**（`编辑器设置 → Run → Window Placement`
   → Embed Game Window），否则看到的还是编辑器里的画面，透明、弹窗位置都不作数。

### 图集边缘外扩（dilate）

Blockbench 的皮肤图集是一堆 UV 岛拼在一张 256×256 的图上，岛与岛之间是空白像素。
把这张图量了一遍：

| | |
| --- | --- |
| 完全不透明 | 20600 texel（31.4%） |
| 完全透明 | 44936 texel（68.6%） |
| 半透明 | 0（alpha 只有 0 和 1 两种） |
| **紧贴图案那圈透明 texel 的平均 RGB** | **(0.000, 0.000, 0.000)** |

**空白是纯黑的，不是白色。** 所以 UV 越界采样混进来的是黑 ——
表现是**一圈偏暗的描边**，不是白边。（这也和渲染数据对得上：
轮廓过渡像素亮度 0.573，比实体像素的 0.712 还暗。）

`_harden_materials()` 里加了运行时外扩：`_dilate_image()` 把不透明像素的 RGB
往相邻透明像素复制，**alpha 保持 0**。这样越界采到的是相邻图案的颜色，
同时 alpha scissor 的裁切位置完全不变（图案不会"长胖"）。
参数是 `dilate_pixels`，默认 2，设 0 即关闭。

实测（同机位，"边缘像素平均亮度 / 实体像素平均亮度"）：

| `dilate_pixels` | 边缘/实体 |
| --- | --- |
| 0（关闭） | 0.757 |
| **1** | **0.771** |
| 2（默认） | 0.771 |
| 4 | 0.770 |

**1px 就已经饱和** —— 因为用的是最近邻采样、UV 精确压在 texel 边界上，
真正会越界的边界像素本来就不多。所以这是个"便宜但收益有限"的保险，
默认给 2px 是为了将来万一改成线性采样或者开 mipmap 时 padding 够用。

**为什么在运行时做，而不是直接改那张 PNG**：`peekdeek_opt.glb` 的贴图是
**内嵌**在 glb 里的（`gltf_to_glb.mjs` 从 `src.images[].bufferView` 复制过去），
Godot 导入 glb 时把它提取成 `peekdeek_opt_0.png` —— 直接改这个文件会在
glb 重新导入时被覆盖。真要落到资产上，得改 `gltf_to_glb.mjs`（Node 侧做 PNG
解码/外扩/重编码）。

### "白色轮廓"的排查结论

按现在的配置渲染，再把透明图按预乘 alpha 合成到深色底、放大 3~4 倍看，轮廓是干净的：

- 全透明区域的 RGB 实测全是 **(0,0,0)**，没有底色被混进来；
- 轮廓过渡像素的平均亮度 **0.573**，比实体像素的 **0.712** 还**暗** ——
  说明它们是"模型色 × 覆盖率"的正常过渡，不是被掺了白色。

也做过四联对照实验（当前配置 / 关高光 / 关超采样 / 关 MSAA，同一机位放大 3 倍），
四种情况都没有出现白色描边，所以白边不是高光或 MSAA 造成的。

**这种情况下最可能是超采样那层偏亮的过渡带**（已经关掉），其次要怀疑的是
显示器/显卡驱动的锐化，以及**看错了地方**——编辑器 3D 视口有它自己独立的
背景与抗锯齿设置，和运行时的效果不是一回事。

### 如果你还看到白边

0. 先确认你看的是**运行中的游戏窗口**，不是 Godot 编辑器的 3D 视口 ——
   编辑器视口有独立的一套背景/抗锯齿设置，和最终效果不是一回事
1. **确认重启了应用** —— 贴图导入参数是导入期生效的，光重启窗口不够，
   必要时删掉 `.godot/imported/peekdeek_opt_0*` 再让 Godot 重新导入一次
2. 检查是不是**显示器/显卡驱动的锐化**（NVIDIA 控制面板的"图像锐化"、
   AMD 的"Radeon Image Sharpening"）在深色桌面上放大了边缘对比
3. `desktop_pet.gd` 里有个 `texture_filter_mode` 参数，默认最近邻，
   想换线性可以直接在检查器里改
4. 如果看到的是**深色**描边（不是白的）—— 先看 `screen_space_aa_mode` 是不是被打开了。
   SMAA / FXAA 在透明背景下会给轮廓掺黑（见上文那一节），调回「关闭」即可

## 动画节奏（整体放慢）

`desktop_pet.gd` 顶部的 **动画节奏** 分组里有三个倍率，都能在检查器里实时调：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `anim_speed` | **0.7** | 所有动画的播放速度倍率（主体和眨眼叠加层一起生效） |
| `blink_slowdown` | **2.5** | 眨眼间隔倍率，越大越少眨眼 |
| `behavior_pace` | **1.3** | 待机 / 散步的时段整体拉长，越大越"懒" |

`anim_speed` 走的是 `AnimationPlayer.speed_scale`，所以顺带做了两件配套的事：

- **走路的位移速度同步缩小**。`_begin_move()` 里 `_speed` 乘了同一个倍率 ——
  不然步频慢下来了、窗口还按原速平移，脚底会明显打滑。
- **动作后的等待时间按 `_beat()` 换算**。原来写死的 `_timer = 0.6` 全部换成
  `_timer = _beat(0.6)`（即 `0.6 / anim_speed`）：动作本身变慢了，等待时间也得
  同比拉长，否则动作还没播完就被打断回待机。
- **眨眼概率除以 `blink_slowdown`**，而不是去改 `blink_chance` 的初值。

想让动作回到原始速度：`anim_speed = 1.0`、`behavior_pace = 1.0`、`blink_slowdown = 1.0`。

## 移动方向与朝向

人物会朝**移动方向**转身，而不是永远正对屏幕：

| 屏幕上往哪走 | 3D 里看到的 |
| --- | --- |
| 向右 | 偏航 -90°，看到侧面 |
| 向左 | 偏航 +90°，另一侧侧面 |
| 向上 | 偏航 0°，**背对镜头**往远处走 |
| 向下 | 偏航 180°，正对镜头走近 |

坐标对照（相机在 +Z 看向原点）：屏幕右 = 世界 +X、屏幕上 = 世界 -Z。
换算就是 `yaw = atan2(-dir.x, -dir.y)`，见 `_facing_target_yaw()`。
**静止时会转回 `FACING_BASE`（正对屏幕）**，所以停下来的样子和以前一致。

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `face_move_direction` | **1.0** | 1 = 完全朝移动方向；0 = 永远正对屏幕（旧行为）；中间值可折中 |
| `allow_vertical_move` | **true** | 会不会往屏幕上下方向走 |
| `vertical_move_weight` | **0.7** | 上下相对左右的出现权重（1 = 同概率） |

### 家（初始位置）与回家引力

桌宠有一个"家"：**启动时就停在那儿**，飘得离它越远，下一次走路越可能朝家的方向走。

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `home_anchor` | **(1.0, 1.0)** | 家的位置，屏幕可用区域的归一化坐标（0~1）：(1,1) = 右下角、(0.5,1) = 底部居中、(0,0) = 左上角 |
| `home_deadzone` | **150** | 离家这么远以内算"在家附近"，不施加任何牵引（像素） |
| `home_pull` | **0.8** | 牵引强度：0 = 关闭（永远随机走）；1 = 远到屏幕半对角线时必然往回走 |
| `drag_sets_home` | **true** | 拖拽放下后把落点当成新的家；关掉则拖拽只是临时挪一下 |

**三种改家的方式**：

1. 检查器里直接改 `home_anchor`（分组「窗口」）；
2. 右键菜单 →「把当前位置设为家」—— 先拖到想放的地方，再用菜单记下来；
3. 直接**拖拽**放下（`drag_sets_home` 打开时）—— 拖到哪儿哪儿就是家。

### 只在小范围走动（不想让她满屏溜达时）

右键 →「位置与窗口」→「只在小范围走动」，或设置面板「窗口与操作」里同一个开关。
开了之后她只在家附近 `nearby_radius`（默认 220px）的方块里转。

两个刻意的设计：

- **已经在圈外不瞬移**：一开开关就把她拽回家，比不管还吓人（安静模式那条注释里
  已经踩过这个坑）。所以规则是"先不夹，等她被回家引力拉着溜达回来再开始管" ——
  看起来就是"她回来了"，而不是被吸过去
- 和**安静模式共用一套机制**（都在 `pet_walk._step_move` 里对活动范围求交），区别只在中心：
  安静模式是"进入全屏那一刻她所在的位置"（自动触发的，更不能瞬移），
  这个就是**家**（你主动开的开关，本来就希望她待在窝附近）。两个同时开着就是取交集

还想更省心的话，同一组里另有「起身走一次的概率」（`move_chance`，默认 0.35）——
调小 = 她起身的次数变少，调到 0 就完全不动了（摸头 / 眨眼 / 呼吸照常）。

> 验：`tools/probe_memory.gd` 的离线段试 `nearby_box()`（中心 / 边长 / 半径填 0 不塌）；
> 真机那次是让她走 400 步，看"有没有一帧跑出圈""在圈外会不会被瞬移""关掉后能不能走远"。

后两种都会写进 `user://pet_home.cfg`（Windows 下是
`%APPDATA%\Godot\app_userdata\桌宠\pet_home.cfg`），下次启动仍停在那儿。
不写回 `scenes/pet.tscn` 是有意的：拖一下就把场景文件改掉太意外，也不好回滚。
想回到出厂设置：右键菜单 →「初始位置恢复右下角」（等价于 `home_anchor = (1,1)`）。

停靠位置算的是**窗口能落到的范围**（可用区域减去窗口自身）再乘锚点，
所以 (1,1) 是右下角贴边、(0.5,1) 是底部居中 —— 窗口大小和任务栏高度都不影响，
停下去不会露出一截在屏幕外。回家引力也是量到"家的窗口位置"的像素距离。

牵引概率从死区处的 0 线性爬到半对角线处的 `home_pull`，所以只是偶尔飘远，
不会刚出门就被拽回去；方向按离家向量的两轴分量加权挑，斜着离家就斜着回去。
实现见 `_home_pos()` / `_home_pull_dir()` / `set_home_here()`，
验证见 `tools/probe_home_pull.gd`（**要带窗口跑**，headless 下 `window_get_size()` 是 0，
停靠位置和"离家多远"都测不出来）。

> 旧实现是"走动时只从正面偏转 ±20°"，所以看着总是大致正对镜头；
> 现在换成真正的转向，`FACING_SWING` 那个常量已删除。

## 性能上做的两件事

`_process()` 里唯一的每帧大头是角色包围盒：悬停检测和"可点区域"每帧各要算一次，
而每次都要遍历 **567 个 `MeshInstance3D`**。改了两处：

| 改动 | 效果 |
| --- | --- |
| 包围盒按 `AABB_REFRESH_FRAMES`（默认 3）帧节流，且一帧内复用 | 每帧遍历次数 2 次 → 约 0.33 次 |
| `_compute_model_aabb()` 改用 `Transform3D * AABB`（C++ 里算），不再自己循环 8 个端点 | `_calibrate()` 启动要按帧采样几百次，那 567×8 次 GDScript 向量变换是启动卡顿主因；改完校准结果逐位一致（`S` 只差 1e-6） |

顺手修了一个**帧率相关的 bug**：窗口位置只能取整像素，原来写的是
`int(_facing * _speed * delta)` —— 60fps 下 46px/s 算出来是 0.77，`int()` 直接截成 0，
**走得动走不动完全看帧率**。现在用 `_move_accum` 把不足 1px 的位移累积起来再取整。
`_update_facing()` 里也把 `rotation.y` 归一到 `[-PI, PI]`，避免连续转向时数值一直累加
（跑一整天后 float32 精度会变差）。

## 几个踩过的坑（改代码前值得看一眼）

1. **`AnimationPlayer.seek()` 不会立刻刷新 3D 变换**
   想采样"角色在动画里到底占多大"时，用 `seek()` 量出来的永远是静止姿势。
   必须让动画真正跑起来、跨帧采样（`_calibrate()` 就是这么做的）。

2. **量包围盒必须用 `global_transform`**
   这个模型的动画驱动的是网格的**祖先**节点（`Root/MAllBody` 等），
   网格自身的 `transform` 一直是静止值。用 `mi.transform` 会永远量到静止姿势。

3. **`owner` 不能乱设**
   给 GLB 实例内部的节点设 `owner`，`PackedScene.pack()` 会把整棵树
   （567 个 MeshInstance3D）**内联展开**写进 `pet.tscn`，而不是留一个
   `instance=ExtResource` 引用——场景文件会从 4 KB 膨胀到 1,900 行。

4. **Godot 4.7 的 `window_set_mouse_passthrough()` 收的是多边形数组**，不是 bool。
   传 `PackedVector2Array()` 表示整窗可点，传一整块矩形表示整窗穿透。

5. **模型的正面朝向 −Z**
   相机在 +Z 看向原点，所以基准旋转是 `PI` 才面向镜头。
   别按数据直觉猜，用 `tools/shoot_pose.gd` 渲一张就知道。

6. **不要用 PowerShell 的 `Set-Content` 改这个 .gd 文件**
   它会把中文写成非 UTF-8，Godot 直接报 `Unicode parsing error`。
   用编辑器或者 UTF-8 安全的方式改。

7. **轮廓白边不在 alpha 上，在贴图的透明区 RGB 上**
   这个模型的 alpha 一直是干净的（半透明像素为 0），
   白边来自"透明 texel 里存着亮色 RGB"被线性过滤掺进边缘。
   所以别去调 MSAA / alpha 抗锯齿，先去量 `tools/probe_ring.gd`。

8. **贴图导入参数是导入期生效的**
   改完 `.import` 要重新导入；只重启游戏窗口是不会生效的。

9. **`tools/*.gd` 这种 `extends SceneTree` 脚本必须有看门狗**
   `--script` 模式下 Godot 不会自己退出：脚本跑完不调 `quit()`，进程就一直挂着。
   更坑的是中途抛错（比如访问了当前版本里不存在的属性），写在函数末尾的 `quit(0)`
   根本执行不到，命令行就会一直等 —— 表现出来就是"跑引擎卡死了"。
   所以每个工具脚本都要在 `_process()` 里数帧数、超时强退
   （`probe_material.gd` 之前漏了，现已补上；它当初就是踩了 `alpha_hash_enabled`
   这个 Godot 4.7 已移除的属性）。

10. **PopupMenu 是独立窗口，坐标是屏幕坐标**
    项目里 `embed_subwindows=false`，所以 PopupMenu 会开成一个真正的系统窗口。
    它的 `position` / `popup(rect)` 用的是**屏幕坐标**，而 `_input` 里拿到的
    `mb.position` 是**窗口内坐标** —— 直接混用，菜单就会跑到屏幕左上角附近去。
    正确写法是补上窗口自身的位置：
    `DisplayServer.window_get_position() + Vector2i(pos)`。

11. **在 PowerShell 里跑 `godot.exe` 不会等它、也收不到它的输出**
    这个 steam 版的 exe 是 **GUI 子系统**构建（目录里没有 `.console.exe`），
    所以用 `& $godot ...` 调用会**立刻返回**，`$LASTEXITCODE` 是空的、stdout 也抓不到
	—— 看起来像"跑了一下就退出、什么都没打印"。其实进程还在后台跑。
    要拿结果有两个办法：`Start-Process -Wait`，或者直接读它的日志文件
    `%APPDATA%\Godot\app_userdata\桌宠\logs\godot.log`（`print()` 的内容都在里面）。

12. **`PopupMenu` 设勾选项的方法叫 `set_item_as_checkable`**，不叫 `set_item_checkable`
    （后者是 Godot 3 的名字，4 里没有，写了会在运行时才报
    `Nonexistent function`）。读回来的是 `is_item_checkable` / `is_item_checked`，
    勾选状态是 PopupMenu 自己存的另一套，改完运行时开关要记得 `_sync_toggle_menu()`。
	在这个版本里想确认 API 到底叫什么，用 `ClassDB.class_get_method_list("PopupMenu")`
    打一遍最快 —— 别照抄记忆里的名字。

    13. **同名函数和成员变量会让整个脚本解析失败，而且报错不点出重名**
        给 `pet_menu.gd` 加了个 `func _status()`，而那个文件里早就有 `var _status: Label`
		（AI 面板的状态文字）。报错长这样：`Could not preload resource script "res://scripts/ui/pet_menu.gd"`
		—— 只说"加载不了"，一个字没提重名，得自己挨个看改过的地方。
        加函数前先扫一眼同名的变量。

    14. **`PackedStringArray` 在这个版本里没有 `join`**
		`PackedStringArray(out).join("\n")` 直接解析失败（`Cannot find member "join"`）。
        拿它拼 `OS.execute` 的多行输出时手写循环拼。想确认某个类型到底有哪些方法，
        用 `--check-only --script <脚本>` 过一个，比跑起来快得多。

	15. **辅助进程会因为"一次没找到窗口"就悄悄退出**
    `Tick()` 返回 `DEAD`（找不到宠物窗口）时原来是**立刻**结束进程 —— 而窗口重建、过渡态
    都可能瞬时如此。它一死，任务栏隐藏的自愈、托盘图标、置顶维持**一起**静默失效，外面看到
	的只是"某个功能不灵了"，而且进程名是 `powershell`，很难联想到它。
    现在连续 ~8 秒都找不到才收摊；Godot 侧每 0.5 秒用 `OS.is_process_running` 查一次，
    真死了立刻重拉（带冷却和次数上限）。

15. **在 GDScript 字符串里写 PowerShell 正则 = 双层转义地狱**
	`-split '\s+'` 写在 `"""..."""` 里，落盘之后就变成 `-split '\\s+'`，PowerShell 把它当成
	"字面反斜杠 + 字母 s"，于是**根本没分割**：想读的 3 个字段被当成 1 个，三个意愿全读成
    false，自愈和托盘通知一起静默失效（查了很久才想到去看落盘文件）。
    现在**避开反斜杠**：写文件那头用单个空格，读的时候 `-split ' '` 就够了。

16. **PowerShell 脚本的 `param()` 少声明参数 = 静默失效**
    `watch` 模式要用到 5 个参数，而 `param()` 只声明了 3 个 —— `$Arg4`/`$Arg5` 因此全是
    `$null`。读取那一步包在 `try/catch` 里，异常被默默吞掉，表现**完全不像参数问题**：
	"托盘图标是系统默认图标"和"菜单开着收不到通知（于是菜单又被她盖住）"两个功能各自坏掉，
    查了很久才想到去看参数个数。
    现在 `watch` 开头先检查参数齐不齐，不齐就把 `ARGS-MISSING` 写进状态文件再退出。
    教训：给辅助脚本加参数时，`param()` 一定要同步。

17. **`--export-release` 的预设名带空格时，参数要整串传**
     `Start-Process -ArgumentList @('--export-release','Windows Desktop', $out)` 会被按空格
     拼开，Godot 收到的是 `-preset Windows`，报 `Invalid export preset name: Windows`，
	 然后**什么都不导出** —— 而目录里那个旧 exe 还在，特别容易误以为"导出成功了"
     （我就在这上面误判过一次：`pet.exe` 的修改时间还停在几十分钟前）。
	 正确写法是整串传：`-ArgumentList '--headless --path "…" --export-release "Windows Desktop" "…\pet.exe"'`，
     或者直接用 `导出exe.bat`。**导出后一定看一眼 exe 的修改时间。**

18. **`:=` 从一个返回 Variant 的表达推断类型会直接报错**
    这个项目把那条警告当错误，所以 `var x := _find(...)`（`_find` 返回 Variant）会报
	`Cannot infer the type of "x" because the value doesn't have a set type`。
    最容易踩的是**在无类型数组上循环**：`for it in items:` 里的 `it.text`、`it.importance`
    全是 Variant，于是 `var n := it.importance * 0.5` 这种写法成片报错 ——
    显式写 `var n: float = ...` 就行。
    另外 **GDScript 的内部类看不到外层作用域**：内部类里调不到外层的静态函数
	（`Item.retention()` 就是这么改成"由外层拿字段代算"的）。

19. **改提示词要用眼睛看整份拼出来的结果**
	给"常识参考"那段加预算裁剪时，我在两处各拼了一次，于是整块常识在提示词里
    **重复出现两遍** —— 这种错在聊天里根本看不出来（她照样答得好好的，只是每次多烧一份 token）。
    所以 `tools/probe_memory.gd` 会把整份人设原文打印出来；改完人设先跑它扫一眼。

20. **规则抽取必须防问句**
	"你还记得我**叫什么**吗？"命中了"我叫…"那条规则，抓回"什么吗"就写进了档案卡，
	从此她认定"主人的名字是什么吗"。修法是给捕获到的值加一张否定表（什么/啥/谁/哪里/多少…）
    和长度上限 —— 规则抽取**宁可漏也不能错**：错的那条会一直留在提示词里，漏掉的下次还能再抓。

## 已知限制

- 走动是**移动窗口**实现的，不是窗口内平移，所以桌宠不会被其他窗口遮挡
  （配合"置顶"体验比较自然）
- 没有做屏幕边缘的"爬墙 / 掉落"物理，撞到边缘就折返
- 模型没有骨骼（skin），是 722 个节点的刚体层级，所以 567 个 draw call
  ——13.6k 顶点、6.8k 三角面，对桌宠来说完全够用
- 聊天走 OpenAI 兼容接口（`user://pet_chat.cfg` 的 `[ai]` 段，默认 DeepSeek 官方 API）；
  没配 key 或服务不可达时她只说本地台词
- 长期记忆**没有语义向量**（DeepSeek 没有 embeddings 接口），检索靠字面匹配 + `TOPIC_HINTS`
  话题扩展表，换个完全不同的说法可能就找不着 —— 稳定的事实走档案卡，那一部分不受影响
- 记忆抽取（规则 + 模型）**都可能抽错**。错条目会留在 `user://pet_memory.json` 里持续影响对话，
  怀疑她记岔了就直接删那个文件（或者只删文件里那一项）
- 「偷看屏幕」要求后端模型是多模态的（`CHAT_MODEL` 名字里带 `vision`），所以默认关着
- 「看看我这边（摄像头）」要 `AIGirlfriend.exe --serve` 在跑、摄像头可用，
  而且菜单里「摄像头」默认是 **关** 的；没开的时候点菜单她只会说
  "我这边还没接摄像头呢～"
- 三条链路（聊天 / 偷看 / 摄像头）**共用一个气泡**，同一时刻只允许一条在跑，
  同时点另一条她只会说"等我先把这句说完～"
- 摄像头那张照片在飞的时候，菜单里再点「看看我这边」是**静默忽略**的
  （气泡还停在"让我看看…"），不会叠一句新的提示
